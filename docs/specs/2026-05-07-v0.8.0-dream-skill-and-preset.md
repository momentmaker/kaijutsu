---

## Problem

**Problem:** kaijutsu's pre-implementation pipeline has a gap. Today the path is `decide / spec-driven-development / planning-and-task-breakdown → incremental-implementation → polish → ship`. There's no formal step BEFORE deciding — no skill that asks "is this idea even worth pursuing? what are we missing? what's the strongest case against?"

**Who feels it:** anyone using kaijutsu for non-trivial features. Without a forced exploration phase, ideas progress on momentum: the first draft becomes the spec becomes the plan, with no structured interrogation of whether the idea is the right shape. Weak ideas survive too long; strong ideas miss adjacent better ideas.

**When:** every non-trivial feature, every architecture decision, every "should we even build this?" moment. The user has been running an ad-hoc version of this manually with a recurring 7-question prompt template (see archived chat history). The pattern works. It deserves to be a skill.

**Today's workaround:** copy-paste prompt template into Claude session. No structure, no recall, no learning, no swarm dispatch.

**Cost of doing nothing:** good ideas never get pressure-tested, weak ideas burn cycles, kaijutsu's pre-implementation phase remains the only stage without a multi-agent QA layer.

## In scope

### `dream` skill — 8 lenses, anti-sycophancy gates, structured output

A new `skills/core/dream/` skill that walks any topic through 8 cognitive lenses. The skill is INVOCABLE standalone (`/dream <topic>` in a single Claude session) AND COMPOSED by a new swarm preset (next section).

**Base lenses (always run):**

| Lens | Asks | Mode |
|---|---|---|
| **honest** | What's actually good and bad about this — no sycophancy, no hedging | critical |
| **fit** | Does this match the project's vibe / current direction / unspoken constraints | contextual |
| **gaps** | What aren't we asking? What hidden assumptions ride along? | meta-critical |
| **wild** | Orthogonal extensions, "what does the 10x version look like?" | generative |

**Extras (opt-in via `--full`):**

| Lens | Asks | Mode |
|---|---|---|
| **adversary** | How does a hostile actor abuse this? Worst-case interpretation? | critical / security |
| **inverse** | What if we did the OPPOSITE? Often "stop NOT-X" is truer than "do X" | generative-via-negation |
| **status-quo** | What if we don't do this? Status-quo strength + opportunity cost of inaction (renamed from `null` to dodge JSON/YAML/Go reserved-word collisions) | critical |
| **time** | Pick a specific date 2 years out. What changed? Is this idea still relevant or quaint? | temporal |

Coverage balance with 8 lenses: 4 critical, 2 generative, 1 contextual, 1 temporal.

### Anti-sycophancy guardrails

Every lens prompt EXPLICITLY forbids:
- "Great question!" / "Excellent point!" / "You're absolutely right!"
- "This is interesting" without specifying WHY
- Hedging: "could be worth considering", "might be helpful"
- Validation-first openings before the actual content

Each prompt opens with: "You are interrogating an idea. The user does not need encouragement — they need a real perspective. Skip pleasantries; jump to substance."

### Stop condition

**Standalone `/dream`** (single Claude session, lenses run sequentially): default = run all 4 base (or 8 with `--full`). Early-out clause: if a lens surfaces a load-bearing insight, the skill prompts "stop here?" before running remaining lenses. The MODEL self-flags `load_bearing: true | false` per JSON output (calibrated examples below); the skill respects the flag and surfaces the prompt — it doesn't override.

**Swarm `jutsu swarm dream`** (parallel fan-out across agents × lenses): no early-out. Cells dispatch in parallel; halting mid-fan-out costs more in coordination than the savings. All cells complete; synthesizer surfaces load-bearing cells visually at the top of the output. v0.8.x may add a streaming/cancellation path once the matrix-cost picture is clearer.

### Load-bearing definition (calibrated)

A finding is `load_bearing: true` if at least ONE of:

- It changes whether the idea should proceed at all (kill-or-continue signal).
- It reveals a constraint that wasn't part of the original framing (the idea must now solve a NEW problem).
- It surfaces a hidden assumption that, if wrong, invalidates the idea's premise.
- The user reading it would say "wait — I didn't know that" or "that changes things" rather than "good point" / "noted".

A finding is `load_bearing: false` for "noted, but doesn't change the path" observations. Models that flag everything as load-bearing produce noisy weighter signal — the calibration above is the prompt-side guardrail.

### Output shape

Each lens emits a JSON ARRAY of objects (multiple thoughts per lens permitted; honest lens often surfaces 3-5):

```json
[
  {
    "lens": "gaps",
    "thought": "We aren't asking how this interacts with users on the legacy auth path...",
    "load_bearing": true,
    "confidence": 0.85
  },
  {
    "lens": "gaps",
    "thought": "Cost projection assumes 4 personas; --full mode triples it.",
    "load_bearing": false,
    "confidence": 0.70
  }
]
```

Synthesizer aggregates into markdown report:
- Per-lens findings sorted by confidence
- Load-bearing insights flagged at top
- Cross-lens consensus surfaced (if 2+ lenses converged on the same insight, that's signal)

Original prose archived to `~/.kaijutsu/dreams/<topic-slug>-<timestamp>.md` for future recall — the dream graveyard.

### `swarm dream` preset — multi-agent × multi-lens

A new swarm preset where each persona runs ALL lenses. Cell math: `agents × lenses` per run. With the default 4-persona dispatch (claude + codex + gemini + one HTTP provider): 4 × 4 = 16 cells; `--full` = 4 × 8 = 32. Persona count is user-controlled via `--personas`; verification examples below show 3-persona runs (12 / 24 cells) since the user's repo runs 3 personas.

```bash
jutsu swarm dream "should we ship a public eval harness in v0.8?"
jutsu swarm dream --personas paranoid-security-claude,default-gemini,claim-auditor-deepseek <topic>
jutsu swarm dream --full <topic>            # opt into 4 extras (8 lenses total)
jutsu swarm dream --lenses honest,gaps,inverse <topic>   # explicit override
```

**Flag precedence:** `--lenses` always wins. If both `--full` and `--lenses` given, `--lenses` overrides — `--full` is shorthand for "all 8", `--lenses` is the explicit list.

**Default `--max-cost`:** swarm dream raises the default from 1.00 to 3.00 (4-cell brainstorm baseline × 4-lens fan-out ≈ 4× cost; 3.00 covers most non-trivial topics with buffer). `--full` raises to 5.00. Users override via `--max-cost N` or `--estimate` first to project actual cost.

Synthesizer's job:
- Cluster matching insights across the matrix (same insight from multiple agents = consensus)
- Surface lens-blind-spots: if all agents converge on the same answer for the same lens, that's a model-shared bias warning
- Surface lens-unique findings: a single agent's gaps lens producing a load-bearing insight that no other cell produced is high-signal

Records to existing v0.7 findings DB via lens-in-summary encoding (no schema change).

### Dream graveyard

`~/.kaijutsu/dreams/` directory of every session as markdown. **Directory mode 0700** (owner traverse only); **file mode 0600** (owner read/write). Same privacy boundary as `~/.kaijutsu/findings.db`.

File naming: `<codebase-fp>-<topic-slug>-<YYYYMMDD-HHMMSS>.md` where:
- `<codebase-fp>` = v0.7 codebase fingerprint (16-char hex or `local-fs:` prefix). Different repos with the same topic get distinct files.
- `<topic-slug>` = first 50 chars of topic, lowercase, non-alphanumeric → `-`, collapse repeated `-`, trim leading/trailing `-`. Implementation detail; spec doesn't pin algorithm beyond "stable + readable + bounded length".

`/dream` checks the graveyard before starting: query for `<codebase-fp>-<topic-slug>-*.md` within 7 days. If a prior dream exists, surface it + apply the **lens-rotation rule**:

- "LEAD lens" = the first lens in the prior dream's run order (recorded in the dream-file header).
- On repeat, drop the prior LEAD lens to last and run the second lens first. So `[honest, fit, gaps, wild]` becomes `[fit, gaps, wild, honest]` on the second dream within 7 days.
- v0.8.x may add user-configurable rotation rules; v0.8.0 ships hardcoded round-robin.

Rationale for **7-day window**: long enough for the user's mental context to evolve (different week, different project state); short enough to recall recent thinking instead of starting cold. Hardcoded in v0.8.0; configurable knob deferred to v0.8.x.

**Cross-codebase recall** is opt-in via `--all-codebases` flag — by default, recall is scoped to the current cwd's fingerprint to avoid cross-project noise.

### v0.7 findings DB integration (lightweight, no schema change)

Each lens output for the swarm dream preset is recorded as one row using the existing schema:
- `persona` field: persona name (unchanged)
- `summary` field prefix: `[lens:<name>] <thought>` (e.g., `[lens:gaps] We aren't asking ...`)
- `severity` field: derived from confidence + load_bearing flag (uses standard kaijutsu vocab — blocker/issue/minor/info)
  - `load_bearing: true` AND confidence ≥ 0.8 → `blocker`
  - `load_bearing: true` AND confidence < 0.8 → `issue`
  - `load_bearing: false` AND confidence ≥ 0.5 → `minor`
  - `load_bearing: false` AND confidence < 0.5 → `info`
- `reasoning` field: the cross-lens consensus or unique-cell flag

Users `jutsu finding accept/dismiss` lens outputs via the existing CLI surface. The recorder treats them like any other finding row. v0.7 weighter naturally tracks per-(persona, preset=dream, codebase) precision — the data accumulates, the proper schema design happens in v0.8.x with that data in hand.

## Non-goals (deferred to v0.8.x)

- **Per-lens precision tracking via dedicated schema column.** v0.8.x adds `lens TEXT` to findings + recorder + weighter once we see what dream-shaped insights look like in practice.
- **Adaptive lens selection by topic.** Static lens choice for v0.8.0; v0.8.x can pick lenses based on topic embedding / past-precision data.
- **Lens-emphasis weighting in synthesizer.** v0.8.0 treats all lens outputs equally; v0.8.x can downweight low-precision lenses per codebase.
- **`receiving-code-review` skill port.** Already deliberated and rejected — kaijutsu trusts the swarm via Pass-2 debate + v0.7 weights.
- **dream-as-eval-corpus.** "Did dream's wild predictions come true?" is a v0.8.x research question, not v0.8.0 ship target.
- **Cross-tool dream sharing.** Personal graveyard only in v0.8.0.

## Open questions

- **Q1 — Standalone skill vs swarm preset: which gets which lens prompts?** Standalone runs in a single Claude session; swarm preset dispatches to multiple agents. Should they share prompts or differ? **Recommendation:** share base lens prompts; swarm preset adds a small per-agent preamble routing to that agent's strength (claude → architecture lens of "fit"; gemini → cross-pattern lens of "gaps"; etc.). Confirm.

- **Q2 — Stop condition trigger: who decides "load-bearing"?** The model itself, or the synthesizer post-hoc? **Recommendation:** model self-flags `load_bearing: true|false` per lens; synthesizer respects but doesn't override. v0.8.x may add user-feedback-driven calibration.

- **Q3 — Graveyard recall scope.** Same topic in any cwd, or scoped to current codebase fingerprint? **Recommendation:** scoped to current codebase via v0.7 fingerprint — different repos rarely have the same topic; cross-codebase recall would surface noise. Override via `--all-codebases` flag.

- **Q4 — Lens-rotation rule on repeat dreams.** Within 7 days of a prior dream on the same topic, what changes? **Recommendation:** swap the LEAD lens. Prior dream led with `honest` → this one leads with `adversary`. Bias toward generative lenses on second dream (often the first dream is critical-heavy). Specifics TBD during implementation.

- **Q5 — Synthesizer prompt for the matrix.** 16-32 lens-cells need to dedupe + surface unique-cell insights. How to phrase? **Recommendation:** synthesizer prompt explicitly asks for three sections: "consensus across lenses" / "load-bearing insights" / "lens-unique cells worth investigating". Refine during Stage 3.

- **Q6 — Caching.** Same topic + same lens set + same cwd → same cache key? **Recommendation:** yes, mirror brainstorm preset's CacheKeyForPrompt; topic + lens set is the input. v0.8.x may add lens-set as a salt.

## Risks

- **Lens fatigue / ceremony**: 8 lenses on every dream = checklist not exploration. Mitigation: stop-condition early-out + repeat-dream rotation rule prevent rote application. Documented prominently in SKILL.md.
- **Sycophancy slip-through**: anti-sycophancy preamble in prompts is a guardrail, not a guarantee. Models may still produce performative agreement. Mitigation: regression test parses prompt files for the forbid list; future v0.8.x may add post-hoc filter via `lie-to-them` style pass.
- **Schema lock-in via lens-in-summary encoding**: if v0.8.x adds proper `lens` column, the encoded format becomes legacy data. Mitigation: encoding is documented as transient; v0.8.x migration parses `[lens:<name>]` prefix from existing summary fields and populates new column.
- **Cost surprise on swarm dream**: cell count is `agents × lenses`. Default 4-persona × 4-lens = 16 cells (~3-4× brainstorm baseline); `--full` 4×8 = 32 cells (~6-8× brainstorm). Exact cost varies with persona mix + topic length. Mitigation: default `--max-cost = 3.00` (was 1.00); `--full` raises default to 5.00; `--estimate` projects concrete numbers before dispatch; explicit warning in CHANGELOG.
- **Graveyard growth unbounded**: dreams accumulate forever. Mitigation: future `jutsu dream clear --older-than 365d` (parallel to `finding clear`); v0.8.0 ships no auto-prune, user manages manually.
- **Topic ambiguity**: "is X worth pursuing?" produces different dreams than "should we use approach A or B?". Skill should NOT prescribe topic shape — but document examples.
- **LLM convergence-by-training**: all 4 agents share LLM training → they may agree wrongly on the same answer for the same lens. Mitigation: synthesizer explicitly flags "all-agents-agreed" as suspicious (model-shared-bias warning), not as consensus signal.

### Lens-in-summary encoding regex

Recorder writes `summary = "[lens:<name>] <thought>"` where `<name>` is one of:
`honest | fit | gaps | wild | adversary | inverse | status-quo | time` (whitelist; closed set in v0.8.0).

v0.8.x migration parses prefix via:

```
^\[lens:([a-z][a-z-]+[a-z])\]\s+
```

Whitelist enforcement on parse. Unknown lens name in legacy data → log + skip (not panic). Documented in v0.8.x migration spec when it lands.

### Lens prompt structure (e.g. `prompts/base/honest.md`)

```markdown
You are interrogating an idea through the HONEST lens. The user does not
need encouragement — they need real perspective. Skip pleasantries.

DO NOT use these phrases:
- "Great question!" / "Excellent!" / "You're absolutely right!"
- "This is interesting" without specifying why
- "Could be worth considering" / "Might be helpful" (hedging)

Your job: identify the REAL strengths and REAL weaknesses of this idea.
Not balanced; not diplomatic. If the idea has 3 strengths and 1 fatal
weakness, write 3 strengths and 1 fatal weakness clearly.

For each finding, emit:
{
  "lens": "honest",
  "thought": "<concrete observation>",
  "load_bearing": <true | false>,
  "confidence": <0.0..1.0>
}

Topic: %s
```

## ADR pointer

ADR will be recorded separately at `docs/decisions/2026-05-07-dream-skill-and-preset.md` during Stage 3. The decision: introduce `dream` as kaijutsu's pre-implementation interrogation primitive, ship as both standalone skill AND multi-agent preset, defer proper schema integration to v0.8.x to avoid lock-in. Reasons: pre-implementation phase has no QA layer today; user already runs an ad-hoc version of this; multi-agent × multi-lens is a uniquely-kaijutsu shape (no other tool has the swarm infrastructure); deferring schema integration follows v0.7's "lock-in is irreversible" principle.
