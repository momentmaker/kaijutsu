# v0.7.0 — Quality fingerprinting + confidence-weighted synthesizer

**Status:** draft, pending `jutsu swarm doc-review`
**Author:** rubberduck
**Date:** 2026-05-06
**Targets release:** v0.7.0
**Touches:** new package `cli/internal/findings/`, schema migration, new `jutsu finding` subcommand group, hook into `cli/internal/swarm/synth.go` for weight application.

---

## Problem

**Problem:** v0.6 swarm dispatches the same N personas with equal voice every time. After 50+ runs against the same codebase, the user has implicit knowledge of which agent's findings consistently land vs which agent's findings consistently get dismissed — but jutsu doesn't capture that signal. Every run starts cold. The 51st run weights gemini's `pattern-consistency` finding the same as it weights gemini's previous 50 findings the user dismissed without action.

**Who feels it:** swarm power users who've run pr-review / doc-review enough times to develop an intuitive sense of "claude is great on auth, codex hallucinates on race conditions in this codebase, gemini's style nits get ignored." That intuition stays in their head. New team members joining the project hit the same N findings the original user already learned to ignore.

**When:** every swarm run after the first ~10 against a given codebase. The cost compounds: the user re-evaluates the same low-quality finding category dozens of times.

**Today's workaround:** mental filtering. User skims findings, ignores the patterns they know are noise. No mechanism for sharing that filter with teammates or with future-self.

**Cost of doing nothing:** swarm value plateaus. Each run produces N findings of which only K are worth acting on; the (N-K) become accepted noise the user trains themselves to skim past. The "more agents = better signal" thesis weakens as noise accumulates uniformly across providers.

## In scope

### Local SQLite findings store

- New file at `~/.kaijutsu/findings.db` (per-user, per-machine — never leaves the machine in v0.7).
- Schema records every finding from every swarm run with denormalized provider/persona/preset/codebase tags so weight computation is a single indexed query.
- Codebase fingerprint resolution chain (first match wins; deterministic across machines):
  1. `git remote get-url origin` succeeds → `sha256(stdout + ":" + git rev-parse --show-toplevel basename)[:16]`. Fork-aware (different basename → different fp).
  2. `git remote get-url upstream` succeeds (no origin) → same SHA256 with upstream URL.
  3. `git remote -v` shows ANY remote → use the alphabetically-first remote URL.
  4. `git rev-parse --is-inside-work-tree` succeeds but no remotes (fresh `git init` / detached worktree / submodule) → `local-git:<sha256(toplevel-abspath)[:16]>`.
  5. Not in a git repo at all → `local-fs:<sha256(cwd-abspath)[:16]>`.
- All paths produce a 16-char hex string; downstream code never special-cases the prefix. Fallback policy enumerated to avoid silent degradation when user runs jutsu in non-standard repo layouts.
- Migration on first invocation: create DB if absent; apply `migrations/NNNN_*.sql` schema. Idempotent.

### Recording layer

- Every `jutsu swarm <preset>` invocation that produces findings writes them to the DB before printing markdown.
- One row per finding (not per run) — supports per-tuple precision math without re-aggregation.
- `run_id` field links findings back to their cache entry (`runs/<key>/`) for replay/debug.
- Best-effort: DB write failures log to stderr but do NOT block swarm output. Quality-fingerprinting is opt-in value, not a critical path.

### User action capture

- New `jutsu finding` subcommand group. **All commands operate on the resolved `codebase_fp` of the current `cwd`** unless `--codebase <fp>` overrides.
  - `jutsu finding list [--run <id>] [--pending] [--all-codebases]` — defaults to last run for current codebase. `--run <id>` filters by run; `--pending` filters to unactioned; `--all-codebases` ignores cwd scope.
  - `jutsu finding accept <id> [--reason "..."]` — marks as true positive. `<id>` is the global `findings.id` autoincrement; `jutsu finding list` displays it as the leftmost column so users can copy-paste.
  - `jutsu finding dismiss <id> [--reason "..."]` — symmetric to accept.
  - `jutsu finding stats [--codebase <fp>]` — per-(provider, persona, preset) precision report scoped to current codebase by default. Header line prints `current codebase fp: <16-char hex>` so users can copy-paste it into other commands.
  - `jutsu finding clear [--codebase <fp>] [--older-than 90d] [--yes] [--dry-run]` — destructive; defaults to `--dry-run` when neither `--yes` nor `--dry-run` is passed; refuses without an explicit affirmative.
  - `jutsu finding export <path> [--codebase <fp>]` — portable JSON dump including `schema_version` field for future import compat.
- Reasons (optional) stored alongside actions for later analysis.
- No PR-comment auto-detection in v0.7 — user explicitly accepts/dismisses via CLI. (PR-comment auto-detection is v0.7.x followup.)

### Confidence weighting

Three-state weight algorithm — important: state 1 preserves v0.6 byte-identical behavior for any user with no findings DB, OR with a fresh DB that hasn't accumulated any actioned findings yet:

| State | Condition (per `(provider, persona, preset, codebase_fp)` tuple) | Weight |
|---|---|---|
| 1. Cold start | DB absent OR `actioned_count == 0` for this tuple | **1.0** (current v0.6 behavior — every agent equal) |
| 2. Bootstrap  | `1 ≤ actioned_count < 10`                                       | **0.7** (slight skepticism without dismissing) |
| 3. Mature     | `actioned_count >= 10`                                          | **precision = accepted / (accepted + dismissed)**, clamped to `[0.05, 1.0]` (never zero — preserve lone-wolf signal) |

- Sliding window: only the most recent 200 actioned findings per tuple count toward precision. Window measured by `action_at` (when user actioned), not `created_at` (when finding was recorded) — drift is detected by recent USER decisions, not by recent dispatch volume.
- Pending findings (no user action) excluded from precision computation.
- `actioned_count = accepted_count + dismissed_count`.

### Synthesizer integration

- `swarm.Synthesize` resolves `(provider, persona, preset, codebase_fp)` for each `AgentResult` before clustering. The persona name is `r.Agent`; the provider is recovered from the persona registry via the same lookup path personaAdapter uses; preset + codebase_fp are passed in.
- `WeightFor(provider, persona, preset, codebaseFp string) float64` returns the per-tuple weight (see "Confidence weighting" above for the three-state algorithm).
- `clusterFindings` ordering changes: secondary sort key becomes `weighted_consensus = sum(unique weights of reporters)`. Each reporter contributes its weight EXACTLY ONCE per cluster, even if the same agent emitted multiple finding rows that merged into the cluster. Prevents one agent's verbosity from dominating the ordering.
- `renderDisagreementTable` displays weight in column headers: `claude (0.85)`. Off by default in v0.7 (gated by `--show-weights` flag on swarm subcommands) so users get the new behavior in `jutsu finding stats` first; v0.7.x or v0.8 may flip the default after weights have been validated against real usage.
- Synthesizer prompt receives `weight` per agent so the model can deprioritize low-weight reporters' findings in the synthesis prose.
- Backward compat: when no findings DB exists OR every tuple is in cold-start state (weight = 1.0), behavior is byte-identical to v0.6.2 — including cluster ordering and table rendering.

### Privacy + portability

- jutsu makes no network calls with the findings DB in v0.7. Local-only by design. (Caveat: user-managed backup pipelines, syncing tools, or multi-user homedir setups that surface `~/.kaijutsu/findings.db` to other readers are outside our control — same boundary as `agents.yaml`.)
- `jutsu finding clear` wipes per-codebase history.
- `jutsu finding export` produces portable JSON; user can manually share / sync via their own pipeline.
- DB file in `~/.kaijutsu/findings.db` — lives in user's home dir (not in any repo); never reachable from a repo's git history. Same-dir co-tenancy with `agents.yaml` is intentional: one user-scoped configuration root.
- DB file mode: `0600` (owner read/write only). Multi-user homedir / auto-syncing backup pipelines that surface the file at non-default permissions get an honest "best-effort" boundary, not a guarantee.
- Findings store DOES include user's code snippets in `summary` / `reasoning` fields (verbatim from agent output). Privacy boundary: same as `runs/<key>/` cache directory — user's machine, user's choice.

## Non-goals

- **No telemetry / phone-home.** Findings DB is forever local in v0.7. v0.8+ may add opt-in anonymized aggregate sharing if usage justifies.
- **No multi-machine sync.** User can `export` JSON and import elsewhere if they want; no built-in sync protocol.
- **No team-shared stats.** Each user's DB is theirs. Sharing requires explicit export.
- **No PR-comment auto-detection.** User explicitly accepts/dismisses via CLI. v0.8 (NOT v0.7.x — needs spec) will add `gh pr comments` parsing for ✓/✗ markers in the kaijutsu-pr-review marker block.
- **No cross-codebase learning.** Weights are per-(provider, persona, preset, codebase_fp). A claude weight learned on repo A does NOT influence repo B. Codebases differ; conflating signals is worse than starting fresh.
- **No model retraining.** Weights influence synthesizer dispatch; they do NOT modify what gets sent to the underlying model.
- **No automatic finding-suppression.** Low-weight findings are still surfaced (downweighted in display) — never silently dropped. User retains visibility.
- **No PII scrubbing.** Findings DB stores summaries verbatim. User responsibility (or `jutsu finding clear`).
- **No GUI / web dashboard.** CLI surface only. v1+ may add a static html report from `jutsu finding stats --html`.

## Acceptance criteria

- [ ] `~/.kaijutsu/findings.db` created on first `jutsu swarm` run that produces findings; subsequent runs reuse it.
- [ ] Schema version table tracks migration state; loader applies `migrations/NNNN_*.sql` files in order; idempotent on re-runs.
- [ ] DB write failures emit a single yellow stderr warning per swarm invocation and DO NOT block the swarm pipeline (quality fingerprinting is non-critical).
- [ ] `findings` table has columns: `id (PK autoincrement, global), run_id, codebase_fp, preset, provider, persona, severity (NOT NULL), file (NOT NULL), line_range (NOT NULL), summary (NOT NULL), reasoning (NULLABLE — agents may omit), confidence (NULLABLE — agents may omit), created_at (NOT NULL DEFAULT now), user_action (NULLABLE: 'accepted'|'dismissed'|NULL=pending), action_at, action_reason`.

- [ ] Composite index on `(codebase_fp, preset, provider, persona, action_at DESC)` — the trailing `action_at` column lets the sliding-window query (`ORDER BY action_at DESC LIMIT 200`) plan-walk the index instead of scanning. ## Open questions (block implementation)

- **Q1 — Codebase fingerprint:** SHA256 of `git remote get-url origin` is stable across clones but ALSO collides for forks. Is that desirable (treat fork same as upstream) or unwanted (keep fork stats separate)? **Recommendation:** stable across clones, separate per-fork → fingerprint = SHA256(remote_url + ":" + git rev-parse --show-toplevel basename). Forks of the same repo share fingerprint only if cloned to identically-named directories. Confirm.

- **Q2 — Bootstrap weight default (0.7):** picked for "slightly skeptical without dismissing." Too high (0.9) → weight has no effect for first 10 runs; too low (0.5) → new tuples undervalued. **Recommendation:** ship 0.7 hardcoded for v0.7; tunability via config file deferred to v0.7.x once we have real-world data on whether users actually want to tune it.

- **Q3 — Sliding window size (200):** balances "fresh enough to reflect drift" vs "stable enough to compute precision." **Recommendation:** 200 hardcoded for v0.7; tunability deferred.

- ~~**Q4 — Weighted-consensus sort tiebreaker.**~~ Resolved in Acceptance: `weighted_consensus desc → ConsensusOf desc → severity desc → key asc`.

- **Q5 — Clean-up policy:** unbounded growth = stale DB. Auto-prune findings older than 1 year? **Recommendation:** v0.7 ships no auto-prune (user explicitly via `clear --older-than`); v0.7.x or v0.8 may add a `prune.toml` config.

- **Q6 — DB location override:** users with shared homedirs (multi-tenant systems) may want non-default DB path. **Recommendation:** v0.7 ships hardcoded `~/.kaijutsu/findings.db`. Env-var override deferred to v0.7.x; multi-tenant users can symlink the path.

- **Q7 — Migration story for schema bumps:** what happens when v0.8 ships a schema change? **Recommendation:** numbered migration files in `cli/internal/findings/migrations/0001_*.sql`; loader applies in order based on `schema_version` table. Forward-only — no down-migration support.

## Risks

- **Cold-start problem:** quality fingerprinting only delivers value after ~50 actioned findings per tuple. New users see no benefit until they've used jutsu enough. Mitigation: explicit messaging in `jutsu finding stats` when tuples are below threshold ("collecting baseline; weighting kicks in after N more findings").
- **Confirmation bias:** if user only dismisses findings they disagree with (and never explicitly accepts the ones they implicitly action upon), precision math underestimates. Mitigation: documentation calls this out + suggests batch `jutsu finding accept` after PR merges.
- **Provider-specific quality drift:** Anthropic / OpenAI / Google update their models periodically; precision learned against claude-opus-4.7 may not apply to claude-opus-5. Mitigation: sliding window of 200 means new model performance dominates after ~50 actioned findings. Could add a `--reset-on-model-change` flag later if drift is sharper than the window catches.
- **Privacy creep:** tempting to add "opt-in anonymized stats sharing" feature, but every step toward telemetry is irreversible. Mitigation: spec explicitly defers all sharing/telemetry to v0.8+ with separate spec + ADR.
- **Weight gaming:** user could manipulate weights by intentionally accepting/dismissing to favor a preferred provider. Mitigation: it's their DB, their tool — gaming hurts only themselves. No countermeasure needed.
- **Schema lock-in:** SQLite schema decisions in v0.7 constrain v0.8+ features. Mitigation: explicit migration framework (Q7) + forward-only design + ADR captures the schema rationale.
- **DB corruption:** SQLite is robust but not bulletproof against power loss / disk failure. Mitigation: `jutsu finding export` recommended in CHANGELOG as periodic backup; `jutsu finding repair` reserved for v0.7.x.
- **Confidence-weighted display surprises users:** seeing `claude (0.45)` next to its findings may erode trust. Mitigation: weight only displayed in `jutsu finding stats` table by default; `--show-weights` opt-in flag for the swarm output. Off by default in v0.7.

### `findings.db` schema (v1)

```sql
CREATE TABLE schema_version (
    version INTEGER NOT NULL PRIMARY KEY,
    applied_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE findings (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id          TEXT NOT NULL,
    codebase_fp     TEXT NOT NULL,
    preset          TEXT NOT NULL,
    provider        TEXT NOT NULL,
    persona         TEXT NOT NULL,
    severity        TEXT NOT NULL,
    file            TEXT NOT NULL,
    line_range      TEXT NOT NULL,
    summary         TEXT NOT NULL,
    reasoning       TEXT,
    confidence      REAL,
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    user_action     TEXT,                           -- 'accepted' | 'dismissed' | NULL
    action_at       TIMESTAMP,
    action_reason   TEXT
);

CREATE INDEX idx_findings_lookup
    ON findings(codebase_fp, preset, provider, persona);
CREATE INDEX idx_findings_pending
    ON findings(user_action) WHERE user_action IS NULL;
```

### Weight computation

```go
// WeightFor returns the precision weight for a (provider, persona,
// preset, codebase) tuple. Returns 1.0 (current behavior) when:
//   - DB is absent
//   - Tuple has 0 actioned findings (cold start)
// Returns 0.7 (bootstrap) when 1 ≤ actioned < 10.
// Returns clamped(precision, 0.05, 1.0) when actioned ≥ 10.
//
// Sliding window: only the most recent 200 actioned findings per
// tuple count toward precision.
func (w *Weighter) WeightFor(provider, persona, preset, codebaseFp string) float64
```

### Synthesizer integration

```go
// In swarm.Synthesize:
weights := map[string]float64{}
for _, r := range results {
    weights[r.Agent] = weighter.WeightFor(r.Driver /* approx */, r.Agent, preset.Name, codebaseFp)
}
// In clusterFindings ordering:
sort.Slice(out, func(i, j int) bool {
    wi := weightedConsensus(out[i], weights)
    wj := weightedConsensus(out[j], weights)
    if wi != wj { return wi > wj }
    if out[i].ConsensusOf != out[j].ConsensusOf { return out[i].ConsensusOf > out[j].ConsensusOf }
    return severityRank(out[i].Severity) > severityRank(out[j].Severity)
})
```

This spec mandates updating `ROADMAP.md` during Stage 5:

### v0.7 — done after this spec ships
- [x] Quality fingerprinting + confidence-weighted synthesizer (this spec)

### v0.8 — committed targets
1. **Anonymized opt-in telemetry.** Sharing aggregated `(provider, persona, preset, precision)` tuples to a shared dashboard. Requires consent flow + protocol design — separate spec + ADR.
2. **PR-comment auto-detection.** `gh pr comments` parsing for `accept`/`dismiss` markers in the kaijutsu-pr-review marker block. Closes the loop without requiring CLI subcommand.
3. **Multi-machine sync.** Optional sync of findings.db across user's machines via user-configured backend (S3, gist, syncthing). User-managed, not jutsu-hosted.
4. **Cross-codebase learning.** Opt-in: weight a new codebase's tuples by similar codebases (same language signature). Privacy-sensitive — needs design.
5. **Multi-stage swarm pipelines.** `jutsu swarm pipeline brainstorm-then-audit` chains presets — needs DSL design (mini-spec).
6. **Live TUI with streaming partial findings.** Depends on streaming support landing in `http_driver` first.
7. **Reverse swarm — spec-vs-implementation drift detector.** New preset that diffs a spec against the PR closing it.
8. **Persona registry + `jutsu install persona:foo`.** Personas as installable artifacts.
9. **Per-skill provider routing.** Skills declare preferred personas; swarm picks accordingly.

## ADR pointer

Architectural decision will be recorded separately at `docs/decisions/2026-05-06-quality-fingerprinting.md` (created during Stage 5 — file does not exist at draft time). The decision: introduce a local SQLite findings store + per-tuple confidence weighting on the grounds that (a) swarm value plateaus when noise accumulates uniformly across providers, (b) the user has implicit precision data from their accept/dismiss actions but no mechanism to capture it, and (c) sliding-window precision math is the simplest model that adapts to model drift without manual retraining. Local-only by design — telemetry is a later, separate decision deserving its own spec + ADR.
