# v0.14.0 — persona browse + preset usage tracking + landing page

**Status**: draft
**Date**: 2026-05-09
**Type**: minor (additive — two small ergonomic adds; no breaking changes)

---

## Why

Three changes land together:

1. **`jutsu agent persona browse`** — the read-only persona-discovery surface deferred from v0.13. Per the v0.13 dream pass: a low-cost, high-leverage subset of the full Persona SDK that closes the most-load-bearing user-facing question ("what personas exist?") without committing to the harder authoring-side work (wizard / lint / cross-agent dispatch). Validates whether persona authoring is actually the bottleneck users hit before committing to v0.14+ Persona SDK. Closes a v0.13 promise.

2. **Preset usage tracking via findings.db** — what v0.13's risk table called the "ghost-town watch" (i.e. monitoring whether the user-preset SDK gets traction or whether built-ins dominate the actual run distribution; if the v0.13 SDK sees ~zero user-preset rows in real findings.db data over 90 days, that's the signal that authoring isn't the bottleneck — informs whether to ship v0.14+ Persona SDK at all). Add a query surface that counts run frequency per preset name + source. Without it, we have no data to make the v0.14+ Persona SDK gate decision against.

3. **`kaijutsu.dev` landing page rebuild** — current `docs/index.html` is a sitegen-generated catalog table with minimal pitch. We've shipped v0.10–v0.13 in fast succession (eval runner, autopilot v2, Tier A presets, Preset SDK) but the landing surface hasn't kept pace. New users hit the page + see a skill table + bounce because the WHY-this-tool-exists framing isn't there. Rebuild the page to communicate the actual ethos: anti-sycophancy at design phase, multi-agent disagreement as a primitive, agent-agnostic skill installation, cost-conscious + transparent, adversarial review as the spine. Mascot brand (chibi monster, sumi-e brushwork, mint-teal #3DDC97 + saffron-rust + charcoal ink, headband kanji 術) already exists; the page needs to LIVE that aesthetic, not just inherit the color palette.

Items 1 + 2 are explicitly small + validate v0.13's reordering bet. Item 3 is bigger creative work but ships in the same release because it's docs-only (no binary impact, no skill changes).

Spec: this doc. Plan: `IMPLEMENTATION_PLAN.md` (3 stages).

## Locked decisions

| # | Decision | Choice |
|---|---|---|
| 1 | `jutsu agent persona browse` output | TTY = aligned table (name / provider / tags / source); pipe = JSON. Auto-flip per existing agent-first convention. `--json` forces JSON regardless. `--yaml` emits paste-into-`agents.yaml`-ready yaml block per persona for copy-paste workflows. |
| 2 | Persona sources surfaced by `browse` | (a) Built-ins from `BuiltinPersonas()` + (b) user-defined from `~/.kaijutsu/agents.yaml` + project's `.kaijutsu/agents.yaml` resolved via existing `agents.LoadGlobalConfig` / `LoadProjectConfig`. NO separate "curated community examples" list in v0.14 — that's a v0.14.x candidate once we see real demand for community-contributed personas (currently zero data). |
| 3 | Persona scope for browse | All personas resolved through `agents.Resolve(global, project)` + the registered built-ins. Single source-of-truth. Source column shows: `built-in` / `user:home` / `user:project`. **Multi-config collision** (a persona name in both home and project agents.yaml): project shadows home (matches existing `agents.Resolve` semantics + matches the v0.13 swarm.yaml precedence rule). Browse surfaces the project version; the home version is hidden under the override. **Built-in shadow** (a persona name in user agents.yaml that matches a built-in): user-defined wins per existing `agents.Resolve` behavior (built-ins are loaded first, user config overlays). Browse surfaces the user version with `source=user:project` or `user:home`. |
| 4 | Filter flags | `--tag <tag>` (exact match against persona's tags list), `--provider <name>` (claude/codex/gemini/deepseek/etc), `--source <built-in|user:home|user:project>`. Combinable. Empty filter = list all. |
| 5 | Persona test + persona new | **Defer to v0.14.x.** v0.14 ships browse only. `jutsu agent persona test <name>` (dry-run validation against a fixed prompt) + `jutsu agent persona new` (interactive wizard) are both useful but not load-bearing. Browse alone gets us the "what personas exist" answer; that's the primary v0.13 promise. |
| 6 | Preset usage tracking surface | New cobra subcommand `jutsu finding stats` (extends the existing `jutsu finding` group). Default: count of (preset) rows in last 90 days. Flags: `--since <duration>` (e.g. `30d` / `1y` — defaults to 90d), `--by <preset|persona|provider>` (group-by axis; default preset), `--source <built-in|user|all>` (source filter; default all; collapses user:project + user:home under `user` per Decision #8). Output: TTY table / JSON pipe. **Group-by axes** (`persona` / `provider`) read directly from the `findings.persona` and `findings.provider` columns — denormalized at recorder-time per `0001_init.sql`'s schema. NO swarm.yaml lookup at query time; the brittleness flagged by Decision #8 only applies to source resolution, not to group-by axes. **NULL handling**: rows with NULL persona/provider (legacy pre-v0.6 rows + recorder edge cases) coalesce to `(unknown)` in group-by output. SQL: `COALESCE(persona, '(unknown)') AS persona`. |
| 7 | findings.db schema | NO migration. `preset` column already exists in v0.7's `findings` table (verified via `cli/internal/findings/migrations/0001_init.sql`). Stats query reads existing data; nothing new written. Source column for filtering: derived at query time by cross-referencing the registered built-in list — built-ins are known-static; anything else is user-defined. |
| 8 | Source resolution at stats query time | The `findings` table doesn't have a `source` column. Stats command derives it from the LIVE registry state at query time: if `preset` is currently registered as a built-in (`registry.UserSource(name) == "" && registry.Find(name) succeeds`) → `source=built-in`; if currently registered as a user preset (`UserSource(name) != ""`) → `source=user`; if `preset` is no longer in the registry at all (e.g. user removed swarm.yaml since the run was recorded; or the row was a retired built-in we no longer ship) → `source=unknown`. **Misclassification edge cases**: (a) user creates preset with built-in name — REJECTED at v0.13 RegisterUserPresets per spec Decision #2 hard-shadow rule, so this collision can't surface at query time; (b) retired built-in — currently zero retired built-ins; if v1.0+ retires one, those historical rows correctly classify as `unknown`. Distinguishing user:project vs user:home is impossible without a `source` column; v0.14 collapses both under `user`; finer-grain split is a v0.14.x candidate via new column + migration. |
| 9 | Marker bump | `0.13.0` → `0.14.0` in `init_agents_fragment`. |

## Out of scope (defer to v0.14.x or later)

- **`jutsu agent persona test <name>`** — dry-run validation against a fixed prompt. Useful but not load-bearing for v0.14's primary "browse what exists" promise.
- **`jutsu agent persona new <name>`** — interactive wizard. Same reasoning.
- **Curated community-examples persona pack** — surfaces in `browse` ONLY when users actually contribute. Don't ship empty.
- **Source split user:project vs user:home in stats** — requires a new `source` column + migration. v0.14 collapses both under `user`; revisit if the granularity matters in practice.
- **Persona registry / `jutsu install persona:foo`** — explicitly NOT shipping (dream flagged persona-as-skill as category error).
- **A/B benchmark on cross-corpus diversity** — v0.12.x homework; unblocks v0.14+ Persona SDK gate; not v0.14 scope.
- **Cross-codebase preset usage learning** — privacy-sensitive design; v0.20+ candidate.
- **Telemetry / community usage dashboard** — explicit user opt-in needed; v0.20+ candidate.

## Build sequence (3 stages)

### Stage 1 — `jutsu agent persona browse`

**Goal**: ship the read-only persona discovery subcommand. Reads existing agents.yaml + built-ins; outputs aligned table (TTY) / JSON (pipe) / paste-yaml (`--yaml`); supports `--tag` / `--provider` / `--source` filters.

**Files**:
- `cli/internal/cli/agent_persona_browse.go` — new cobra subcommand attached to the existing `jutsu agent` cmd group. RunE: load resolved agents config + built-ins, apply filters, render output.
- `cli/internal/cli/agent_subcommands.go` (modify) — `cmd.AddCommand(newAgentPersonaBrowseCmd())` under the existing `agent` cmd construction. Verify there's an existing persona-related cobra group; if not, add a `persona` parent.
- `cli/internal/agents/registry_query.go` — new helper `BrowsePersonas(filters BrowseFilters) []BrowseRow` that returns the merged + filtered list. Pure function over `Resolved`; cli pkg renders the output.

**Public API shape** (new):

```go
// cli/internal/agents/registry_query.go
package agents

type BrowseFilters struct {
    Tag      string // exact match against persona.Tags; empty = no filter
    Provider string // exact match against persona.Provider; empty = no filter
    Source   string // built-in | user:home | user:project; empty = no filter
}

type BrowseRow struct {
    Name         string   `json:"name"`
    Provider     string   `json:"provider"`
    Tags         []string `json:"tags"`
    Source       string   `json:"source"`
    SystemPrompt string   `json:"system_prompt"` // truncated for table output, full for JSON/yaml
}

func BrowsePersonas(resolved *Resolved, builtins map[string]*Persona, filters BrowseFilters) []BrowseRow
```

**Success criteria**:
- `jutsu agent persona browse` lists every built-in + user-defined persona on TTY in a sorted table (alphabetical by name).
- `jutsu agent persona browse --json` emits a JSON array; same data.
- `jutsu agent persona browse --yaml` emits each persona as a yaml block ready to paste into `agents.yaml`. **Concrete format**: a top-level `personas:` map with each persona keyed by name; sub-keys mirror `~/.kaijutsu/agents.yaml` schema (`provider:`, `system_prompt:`, `tags:`, `model:` if set). Test pins this layout against a fixture.
- `jutsu agent persona browse --tag security` filters to personas with `security` in their tags list.
- `jutsu agent persona browse --provider deepseek` filters to deepseek-backed personas.
- `jutsu agent persona browse --source built-in` filters to built-ins only.
- All filter flags combinable.
- Empty filter → all personas.
- Auto-flip: pipe detection chooses JSON output without explicit flag.
- **TTY table truncates `system_prompt` to ≤ 60 chars + ellipsis** (avoids line-wrap noise on multi-line prompts). JSON and `--yaml` output preserve full text. Test pinning the TTY truncation behavior + the JSON/yaml full-text behavior.
- All existing tests stay green.

**Public API shape** (new):

```go
// cli/internal/findings/stats.go
package findings

type StatsOpts struct {
    Since  time.Duration // window from now back; 0 = all-time
    By     string        // "preset" | "persona" | "provider"; default "preset"
    Source string        // "built-in" | "user" | "all"; default "all"
}

type StatsRow struct {
    Group  string // preset/persona/provider name
    Source string // "built-in" / "user" — derived for preset rows; "" for non-preset rows
    Count  int
}

func Stats(store *Store, opts StatsOpts) ([]StatsRow, error)
```

**Success criteria**:
- `jutsu finding stats` shows a count-by-preset table for the last 90 days.
- `jutsu finding stats --since 7d --by persona` groups by persona over the last week.
- **Duration parsing**: `--since` accepts `<N>d` / `<N>w` / `<N>mo` / `<N>y` shorthand (custom parser; Go's `time.ParseDuration` does not support these units). Sub-day grain (`30s` / `5m` / `2h`) ALSO accepted via direct `time.ParseDuration` fall-through.
- `jutsu finding stats --source user` filters to user-defined presets only (collapses project + home).
- TTY = aligned table; pipe = JSON.
- Empty findings.db → "(no recorded runs in window)" message + exit 0 (NOT error).
- `jutsu init` writes AGENTS.md fragment with `version=0.14.0`.

#### 3a. Dream pass on ethos — LANDED

**Locked direction (post-dream):**

1. **Above-the-fold framing**: lead with **portable cross-vendor swarm.yaml primitive**, NOT "multi-agent". Time lens consensus (4 agents): multi-agent becomes commodity by 2028 as vendor IDEs ship native review; cross-vendor portability is the durable moat. One-sentence pitch tests against "would a senior IC say 'oh, that's different'?" — not "AI-powered" / "transform" / "revolutionize".

2. **Page structure** (extends current docs/index.html, NOT big-bang redesign per 3-agent fit/status-quo consensus): hero (above-the-fold pitch) → single-agent failure-mode demo (concrete artifact: a sycophancy-prone single-agent output side-by-side with a kaijutsu disagreement-table) → quickstart (curl install + 1 swarm command) → cross-vendor portability section (`swarm.yaml` works on claude/codex/gemini agents) → cost-per-bug-found framing → trust model (sigstore signing, install gates) → skill catalog (preserved, demoted to a later section) → contributing/footer.

3. **Voice**: terse, technical, code-block-heavy, show-don't-tell. **Some warmth allowed** — discount the all-agents-agreed "no aspirational voice ever" warning (lens-blindspot: LLMs over-index on this; Linear/Raycast/Arc broke this rule profitably). NO inflated claims; NO marketing-speak words.

4. **Cost framing**: "cost per bug found" (e.g. "$0.12 / 14s for an architecture flaw caught"), not "cost per call". Address the 3x-API-cost objection inline at the cost section, NOT as a standalone top-line feature. 3-agent gaps/adversary consensus.

5. **Mascot + visual identity**: keep the chibi mascot but **smaller hero placement** (anchor moment, not 600px); kanji 術 + asymmetric ink-brush primary; charcoal/paper/ink primary palette; mint-teal #3DDC97 as ACCENT only (3-agent honest consensus that current mint-dominant palette risks "cute toy" framing — discount the lens-blindspot warning but still constrain). Time lens warning: avoid trend-saturated colors; if the brand needs a refresh later, easier to swap an accent than a hero.

6. **Receipt-driven trust** (THE proof point per paranoid honest 0.85): every release page links to the actual swarm pr-review that reviewed itself. Embed ONE real disagreement-table screenshot from a v0.13 release pr-review. Receipts > rhetoric. The `~/.kaijutsu/dreams/` and `findings.db` corpus IS the asset.

7. **Drop "pre-alpha" framing** anywhere user-visible. Page that says pre-alpha + ships v0.13 + autopilot + Preset SDK reads as abandoned (paranoid 0.80, brainstorm 0.75). Internal contributor docs (CLAUDE.md, AGENTS.md) keep the framing; landing page does not.

8. **NO "reviewed by N LLMs" badge** (2-agent adversary consensus 0.85): invites mockery + falsifiability attack ("three stochastic parrots agree" tweet writes itself). Replace with concrete artifact: link/embed a specific PR-review run with a real disagreement-table.

9. **Sitegen regen as hard constraint**: extend `cli/cmd/sitegen/main.go` to add a hero-block template hook BEFORE the catalog table. Catalog continues to render; hero block is the new addition. CI's lint-skills.yml drift check stays valid because skills.json wiring unchanged.

10. **Audience = senior IC engineers** (both skill author + skill user). Team-lead/EM/buyer audience explicitly deferred to v0.20+ (per gaps consensus that mixed audiences = muddy CTA).

11. **Avoid "swarm" as headline marketing word** — vendor definitions of "agentic" may diverge by 2028 (gemini time lens 0.80). Use "multi-model" / "cross-vendor agentic CI" / "kaijutsu" itself for headline framing; "swarm" stays as the existing CLI command name (unchanged).

12. **Cynical-read defense**: explicitly address the "this is just a wrapper around OpenAI/Anthropic APIs" reading (gemini adversary lens). Show what's NOT a wrapper: cross-vendor portability, findings.db quality fingerprinting (per-agent confidence weights from real precision data), cost transparency, Preset SDK, dream lens-blindspot warnings. One section, factual, no defensive tone.

13. **Inverse path explicitly considered + rejected**: "no landing page, just README + asciinema" (3-agent inverse consensus, 0.85) is coherent — Anthropic MCP launched on docs alone. Rejected because kaijutsu's mascot brand + sumi-e identity are sunk-cost worth using AND the page provides discoverability anchors (skill catalog, quickstart) that README+asciinema can't.

14. **Success metric for the page**: skills-installed-via-`jutsu install`-in-real-codebases (qualitative for v0.14; opt-in telemetry deferred to v0.20+ per existing roadmap). Tracked via GitHub stars + Homebrew install count + skill-import frequency in opt-in PR comments. NOT tracked: vanity metrics (page views, time on page).

**Lens-blindspot warnings preserved as guardrails** (apply when implementing): no over-correction toward "stripped voice" (counter-evidence exists); no over-correction toward "serious-aesthetic only" (Linear / Raycast / Arc); the 2028-multi-agent-becomes-commodity prediction may not hold (vendor coordination could fail) — landing page direction works either way because cross-vendor portability is durable in BOTH futures.
