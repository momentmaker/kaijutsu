## Problem

**The gap:** kaijutsu ships skills + a swarm primitive but no way to ANSWER "does this skill / persona / preset actually make the model better?" Skill authors guess. Reviewers eyeball. The v0.7 weighter measures POST-hoc trust (user accept/dismiss), not pre-shipping quality. ROADMAP v0.3 had `[ ] jutsu eval` and never shipped.

**Who feels it:**
- Skill authors who can't prove a v1.0.0 ship beats v0.0.1
- Maintainers reviewing community PRs without measurable lift signal
- Users picking between alternative skills (e.g. `pr-review` vs `code-review-and-quality`) with no evidence
- Future v0.3 trust tier: signed-core skills should beat unsigned-community ones on shared evals before sigstore stamp

**Today's workaround:** vibes. PR descriptions claim "I tested it manually." Adversarial swarm pr-review on the skill itself catches some bugs but not regressions.

**External landscape:** [agent-skills-eval](https://github.com/darkrishabh/agent-skills-eval) by darkrishabh ships a TypeScript runner for the agentskills.io-format `evals/evals.json` shape. It does **per-skill** eval (with_skill vs without_skill, judge-graded). MIT-licensed. Active. Used by some agentskills.io community.

**Cost of doing nothing:** kaijutsu's "trust" story is weaker than it should be. Sigstore verifies WHO signed; we have no answer for "does the signed thing actually work."

## In scope

### 1. `evals/evals.json` schema parity (port, not fork)

Native Go parser for the agent-skills-eval evals.json shape:

```json
{
  "skill_name": "string",
  "evals": [
    {
      "id": "string",
      "name": "string",
      "prompt": "string",
      "files": ["string"],
      "expected_output": "string",
      "assertions": ["string"]
    }
  ]
}
```

Fields:
- `skill_name` REQUIRED — must match the parent skill's name
- `evals` REQUIRED — array of eval cases
  - `id` REQUIRED — stable identifier (used as artifact subdir)
  - `name` REQUIRED — human display name
  - `prompt` REQUIRED — the eval prompt
  - `files` OPTIONAL — files attached to the prompt
  - `expected_output` OPTIONAL — description of desired behavior; auto-promoted to judge assertion if no `assertions:` provided
  - `assertions` OPTIONAL — explicit grading criteria

**Compat principle:** kaijutsu eval MUST read agent-skills-eval evals.json files unchanged. Skill authors targeting both ecosystems write one schema. Pinned compat tested via `cli/internal/eval/testdata/agent-skills-eval-fixtures/` (small set captured from upstream README + skill examples).

### 2. Single-skill eval (parity with agent-skills-eval)

`jutsu eval skill <skill-path-or-name>` runs every eval in the skill's `evals/evals.json`:

For each eval:
1. Run target model TWICE — once with SKILL.md loaded into context (`with_skill`), once without (`without_skill`).
2. Judge model grades both outputs against `assertions` (or `expected_output` promoted).
3. Result: pass/fail per side, judge reasoning, timing, cost.

Output:
- Workspace dir: `<workspace>/iteration-N/` (matches agent-skills-eval layout for tooling compat)
- `iteration-N` numbering: **monotonic per workspace, starting at 1**. New runs scan existing `iteration-*` dirs and pick the next integer. Concurrent-run collision handling: lock file `<workspace>/.eval-lock` (contents: `<pid>\n<unix-ts>\n`) held during a run; second concurrent invocation errors with "another eval is running in this workspace". **Stale-lock policy:** lock is considered stale when (a) PID in lock file no longer exists, OR (b) lock file mtime is >2 hours old. Stale locks auto-clear on the next invocation with a stderr warning. CI runners that crash mid-eval leave a stale lock; the next run picks up cleanly.
- `<workspace>` directory ownership: `.kaijutsu/eval-runs/` is reserved for eval runs only. Future kaijutsu features must NOT write into `eval-runs/`. v0.7 findings.db lives at `.kaijutsu/findings.db` (sibling, not nested) — no collision.
- `meta.json` — run metadata (target, judge, models, timestamp, judge prompt template version)
- `benchmark.json` — rolled-up pass/fail per skill
- `eval-<id>/<side>/` — per-side artifacts (output, timing, grading). `<side>` directory name varies by eval shape (Stage 2): `with_skill/`/`without_skill/` for skill evals; `<persona-name>/` for per-persona; `<mode-name>/` for per-preset; `with_skill_in_swarm/`/`without_skill_in_swarm/` for swarm-skill.
- `report/index.html` — static HTML report (single-page, embeds JSON; no infra to host)

#### `expected_output` auto-promotion to assertion

Spec contract: when an eval has no `assertions:` array but provides `expected_output`, the runner synthesizes a single assertion via this template:

```
"Output should satisfy expected behavior: <expected_output verbatim>"
```

The wrapped phrasing matches the judge prompt's "ASSERTION:" expectation; no other transformation. agent-skills-eval upstream uses verbatim copy; we wrap to give the judge clearer framing. Compat tested via `testdata/agent-skills-eval-fixtures/`.

#### Multi-assertion handling

When an eval has multiple `assertions:`, the runner makes ONE judge call PER assertion. Result `pass = true` only if EVERY assertion passes. Per-assertion reasoning preserved in `grading.json` for drill-down. Cost = N × per-judge call where N = assertion count.

CLI:
```bash
jutsu eval skill <path-or-name> --target claude --judge gemini --strict
jutsu eval skill --target deepseek --judge claude --report-output /tmp/eval-out --no-baseline-side
```

Flags (mirror agent-skills-eval where possible):
- `--target <name>` — model used to execute the eval prompt. Required when zero agent CLIs detected; otherwise defaults to first available with the chosen target echoed to stderr for reproducibility.
- `--judge <name>` — model used to grade outputs (defaults to `claude`; `~/.kaijutsu/eval.yaml` `judge:` field overrides).
- `--baseline-side` (default ON) / `--no-baseline-side` — controls whether the `without_skill` side runs alongside `with_skill`. Renamed from `--baseline` in early spec drafts to disambiguate from per-persona/preset `--baseline-persona` / `--baseline-mode` flags introduced in §3.
- `--strict` — has TWO modes; both apply per-shape:
  - **Stateless** (default, no `--baseline-from`): regression = `with_skill` fails an assertion that `without_skill` passed in the SAME run. Per-skill only; for swarm shapes the baseline/challenger pair plays the same role.
  - **Stateful** (`--baseline-from <git-ref>` flag): regression = current run's `<challenger>` fails an assertion that the run-at-`<baseline-from>`-ref passed. Reads `eval-baseline.json` artifact from a prior tagged run. CI workflow uses this mode against the previous tag's baseline. First-run-with-coverage policy: if no stored baseline at `<baseline-from>` exists, exit 0 with stderr warning "first eval run; --strict has no baseline to compare". Subsequent runs hard-fail. Operator gate: `--accept-baseline` is required to seed a NEW baseline-of-record on a tag where any eval failed (without it, broken-floor seeding is rejected).
  Both modes share exit codes: 0 = no regression, 1 = regression detected.
- `--max-cost <USD>` — abort the eval suite if estimated cost exceeds this cap. Default `$20.00`. Mirrors v0.9 dream cost guard.
- `--baseline-from <git-ref>` — stateful `--strict` mode (see `--strict` above). Names a tag/SHA whose prior eval-baseline.json artifact is the regression-comparison source. Without this flag, `--strict` is stateless (within-run baseline-vs-challenger).
- `--accept-baseline` — operator gate. Required to seed a NEW baseline-of-record on a tag where any eval failed; without it, broken-floor seeding is rejected with a stderr error. v0.10's safety against "first run accidentally commits failures as canonical."
- `--workspace <dir>` — artifact root (default `./.kaijutsu/eval-runs/`). Single canonical term — earlier draft used `<eval-output>` interchangeably; that alias is dropped.
- `--include <glob>` / `--exclude <glob>` — eval-id filters.
- `--concurrency <N>` — parallel evals (default 4). Concurrency disclaimer: timing fields in artifacts are wall-clock and influenced by concurrency; pass-fail is the load-bearing signal.
- `--report` (default ON) / `--no-report` — toggle HTML generation.

### 3. Swarm-shape eval (kaijutsu-native)

The differentiator. Beyond per-skill, kaijutsu evals THREE shapes that single-target eval can't measure:

#### 3a. Per-persona eval

`jutsu eval persona <persona-name>` measures: does `paranoid-security-claude` beat `default-claude` on auth-bug-finding?

Eval shape: same `evals.json` schema BUT runs against TWO personas instead of with_skill/without_skill. The eval cases carry the SAME prompt + assertions; only the persona changes.

Use case: skill authors validating that their custom persona prompt makes the model BETTER at the task than default-<provider>. Without this measurement, "I wrote a custom persona" is unbacked claim.

#### 3b. Per-preset eval

`jutsu eval preset <preset-name>` measures: does `dream` Pass-2 (`--mode full`) beat Pass-1 on idea-interrogation tasks?

Eval shape: per-eval prompt + assertions, runs against the preset's QUICK and FULL modes. Or against two preset variants (e.g. `pr-review` vs `pr-review --strict`).

Use case: validates whether the +N% cost of `--mode full` actually buys measurable lift.

#### 3c. Per-(skill, swarm) eval

`jutsu eval swarm-skill <skill> --preset pr-review` measures: when the `dream` skill is loaded into a `pr-review` swarm run, does that combination outperform pr-review without dream?

Eval shape: same eval cases run through the full swarm pipeline (multi-agent dispatch + synthesizer). Compares with_skill_in_swarm vs without_skill_in_swarm.

Use case: skills that compose into larger workflows (e.g. `dream` feeds into `decide` which feeds into `spec-driven-development`) — measure end-to-end lift, not just isolated skill performance.

#### Schema extensions for swarm shapes

The agent-skills-eval `evals.json` doesn't model multi-agent. We extend WITHOUT breaking compat:

```json
{
  "skill_name": "dream",
  "evals": [
    {
      "id": "single-agent-baseline",
      "prompt": "Should we ship X?",
      "assertions": ["surfaces at least one load_bearing finding"]
    }
  ],
  "kaijutsu": {
    "swarm": [
      {
        "id": "pr-review-with-dream",
        "preset": "pr-review",
        "diff": "fixtures/sample.diff",
        "baseline": "without_skill",
        "challenger": "with_skill",
        "assertions": ["catches the auth bug at line 42"]
      }
    ],
    "personas": [
      {
        "id": "honest-vs-default",
        "baseline": "default-claude",
        "challenger": "honest-deepseek",
        "prompt": "Pre-implementation review of feature Y",
        "assertions": ["honest-deepseek surfaces concerns default-claude misses"]
      }
    ],
    "presets": [
      {
        "id": "dream-quick-vs-full",
        "preset": "dream",
        "baseline": "quick",
        "challenger": "full",
        "prompt": "Should we ship X?",
        "assertions": ["full mode surfaces a load_bearing finding quick missed"]
      }
    ]
  }
}
```

**Per-shape baseline contract:** every `kaijutsu.*` block names a `baseline` and a `challenger`. Reports render `<baseline>/` and `<challenger>/` artifact dirs (e.g. `default-claude/` + `honest-deepseek/` for personas; `quick/` + `full/` for presets). `--strict` regression definition for these shapes: `<baseline>` passes an eval that `<challenger>` previously passed, but the new `<challenger>` run fails it. Baseline-as-canary: regression in the challenger surfaces immediately. Spec aligns persona/preset/swarm-skill semantics under one rule.

Top-level `evals[]` block stays agent-skills-eval-shape (tools targeting that ecosystem read it unchanged). Kaijutsu-specific blocks under `kaijutsu.*` are ignored by upstream tools, parsed by `jutsu eval`. Forward-compat principle.

### 4. Judge dispatch via existing agent driver layer

No new judge-model integration. Reuses v0.6 multi-provider drivers:
- `--judge claude` → uses claude CLI driver
- `--judge default-deepseek` → uses HTTP driver via persona registry

(MCP-driver judges are out-of-scope for v0.10 — deterministic peers like semgrep can't grade prose. Future eval primitive `jutsu eval rule-judge` may surface them when assertion-types differ.)

Judge prompt template (v0.10 default):

```
You are grading whether a model output satisfies an assertion.

ASSERTION: {assertion}

OUTPUT:
{output}

Return ONLY a JSON object:
{
  "pass": true | false,
  "reason": "1-2 sentence explanation citing specific output text"
}
```

Per-skill override: `evals/judge.md` in the skill's directory replaces the default template. **Required placeholders** (validated at load time): `{assertion}` and `{output}`. Override missing either placeholder = hard-fail at parse time with a clear error. Without validation, a malformed override silently emits broken judge prompts and grading misfires. The `evals/judge.md` path is reserved for eval-runner overrides; the skill loader does NOT load `evals/` into SKILL.md context (one-line invariant; documented in `cli/internal/install/install.go`).

#### Judge JSON parse-failure recovery

Models routinely emit prose, ```` ```json ```` fences, or malformed JSON despite the "Return ONLY a JSON object" instruction. The runner extracts the JSON via a tolerant parser:
1. First pass: `json.Unmarshal` on the raw output.
2. Second pass (if 1 fails): regex-extract the first balanced `{...}` block, retry parse.
3. Third pass (if 2 fails): retry the judge call ONCE with a stricter prompt suffix ("Your previous output was not valid JSON. Return ONLY: {\"pass\": true|false, \"reason\": \"...\"}").
4. On 3rd failure: mark the assertion as `"indeterminate"` in `grading.json` (NOT pass, NOT fail). `--strict` treats indeterminate as a failure to err on the side of safety. Counts visible in `benchmark.json` as `indeterminate: N` so users can spot judge-flakiness patterns.

#### Multi-assertion handling

When an eval has multiple `assertions:`, the runner makes ONE judge call PER assertion. Result `pass = true` only if EVERY assertion passes. Per-assertion reasoning preserved in `grading.json` for drill-down. Cost = N × per-judge call where N = assertion count.

#### `--max-cost` estimation method

Runs upfront BEFORE dispatching any model calls. Estimate formula:

```
estimated_total = sum_over_evals(
  (sides_count * (target_input_tokens + target_output_tokens) * target_rate) +
  (sides_count * assertions_count * (judge_input_tokens + judge_output_tokens) * judge_rate)
)
```

- `sides_count` = 2 (with/without baseline) or 1 (`--no-baseline-side`).
- Token estimates: `EstimateTokens` from v0.6 cost.go, ~4 chars/token heuristic. Output tokens estimated as 2× input by default (overestimate to keep `--max-cost` a safety belt rather than precise).
- Rates: per-provider from `swarm.cost.go`. Document staleness: prices update with each release; estimates drift between releases.
- **Default raised to $20** (was $5 in early draft) to accommodate multi-assertion suites: 10 evals × 2 sides × 5 assertions × $0.005/1k × ~3000 tokens ≈ $1.50 per eval suite, leaving margin for larger suites + judge model variance.
- Mid-suite overrun: if actual costs cross the cap during dispatch (per-call cost exceeds estimate by >2×), abort the suite + emit a stderr warning. Already-completed evals' artifacts are kept; pending evals are skipped.

### 5. HTML report generator

Single-file static HTML with embedded JSON. No external deps. Generated in `<workspace>/iteration-N/report/index.html`.

Sections:
- Summary table — skill × eval × side (`<baseline>/` vs `<challenger>/` per the shape's contract) → pass/fail
- Per-eval drill-down — full prompt, both outputs side-by-side, judge reasoning per assertion
- Cost + timing rollup — total $ + wall-clock per side. Timing is wall-clock (concurrency-influenced); cost is per-judge-call summed.
- Diff view — when both sides ran, line-level diff highlighting what changed between baseline and challenger outputs. **Algorithm:** line-by-line LCS, 200-line truncation per side, non-deterministic noise stripped via a fixed regex set (timestamps `\d{4}-\d{2}-\d{2}T...Z`, run-ids `[A-Za-z0-9]+:[0-9]+`, kaijutsu marker comments). Reasoning diff (judge-side) deferred to v0.10.x.

Style: minimal CSS (~200 lines), no JS framework. Renders offline. Drop-in for `jutsu publish` to attach as PR comment artifact.

### 6. CI integration

`.github/workflows/eval-skills.yml` — optional matrix-mode runner on tag:
- For each `skills/core/*` with an `evals/evals.json`: run `jutsu eval skill <name> --strict`.
- Fail the release if any core skill has a `strict`-mode regression.
- Soft warn (not fail) for community skills.

Triggered manually via `workflow_dispatch` for nightly runs in a future iteration.

## Out of scope for v0.10.0

- **Eval results in findings.db** — feeds the v0.7 weighter. v0.10.x candidate; current weighter measures user accept/dismiss, not synthetic eval pass/fail. Different semantics; need an ADR.
- **Cross-eval diffing** ("v1.0.0 of skill X now fails 3 evals it passed in v0.9.5") — requires eval-result history, separate storage. v0.11+.
- **Judge model ensembling** (multiple judges + majority vote) — academic interest; defer until single-judge results are noisy enough to justify.
- **MCP-driver judges for prose grading** — MCP servers are deterministic peers; grading nuanced output isn't their shape. Future eval primitive (e.g. `jutsu eval llm-judge` vs `jutsu eval rule-judge`).
- **Eval marketplace / shared eval suites** — `jutsu install eval:foo` to import third-party evals against your skills. v1.0.
- **Live dashboard UI** — static HTML is enough for v0.10. Pages-hosted dashboard is v0.10.x site work.
- **Auto-generation of evals.json from skill description** — "infer eval prompts from the skill's description text." Tempting, but generates fake confidence in fake evals. Skill authors write evals; we don't auto-fabricate.

## Migration strategy

1. **No DB migration required for v0.10.0** — eval artifacts live on disk under `<workspace>/iteration-N/`, not in findings.db. v0.10.x candidate: optionally promote eval results into findings.db so the v0.7 weighter can incorporate synthetic eval signal alongside user accept/dismiss. Schema for that integration TBD via ADR; out of scope here.
2. **Existing skills without evals/evals.json** — `jutsu eval skill <name>` warns + exits 0 (skill not eval-covered yet). No breaking change.
3. **agent-skills-eval users** — their evals.json files run unchanged via `jutsu eval skill <path>`. We're additive, not competitive.
4. **Eval workspace path** — defaults to `./.kaijutsu/eval-runs/`. Add to `.gitignore` template in `jutsu init`.

## Open questions (for doc-review)

(Several questions from the v1 draft were resolved by the doc-review pass and are now baked into the spec body. Remaining open questions:)

1. **Should `jutsu eval` write findings into findings.db?** Pro: closes the loop with v0.7 weighter. Con: synthetic eval pass/fail ≠ user accept/dismiss; mixing them pollutes the precision signal. **Tentative: NO for v0.10**, separate ADR for v0.10.x integration.

2. **Should we offer `jutsu eval bench` for cross-skill comparison?** Run the same eval against multiple skills. Useful for "which skill is best at X?" Defer to v0.10.x.

3. **Forward-compat verification with strict upstream parsers.** kaijutsu.* extension blocks pass through permissive JSON parsers but a strict JSON Schema with `additionalProperties: false` rejects them. Stage 2 adds `TestKaijutsuExtensionBlock_IgnoredByUpstreamShape` to run a kaijutsu-extended evals.json through agent-skills-eval's actual `npx` parser as a compat sanity check. Until that test runs green, "forward-compat" is a claim, not a guarantee.

4. **HTML diff view algorithm.** Line-level diff with 200-line truncation per side; non-deterministic noise (timestamps, run-ids) stripped via a fixed regex set. Open: should the diff also try to surface "judge reasoning differences" between sides, or stay pure-output? Tentative: pure output for v0.10; reasoning diff in v0.10.x.

(Resolved during doc-review: default target/judge handling, baseline-per-shape contract, --max-cost flag, --strict semantics for swarm shapes, iteration-N numbering, expected_output auto-promotion shape, multi-assertion judge handling, --baseline flag rename to --baseline-side. See spec body §2 + §3 for definitive wording.)

## Verification (end-to-end)

```bash
# 1. Single-skill eval, agent-skills-eval-shape
jutsu eval skill skills/core/dream --target claude --judge claude
ls .kaijutsu/eval-runs/iteration-1/                 # meta.json, benchmark.json, eval-*/, report/
open .kaijutsu/eval-runs/iteration-1/report/index.html
                                                    # → renders side-by-side with_skill vs without_skill

# 2. Per-persona eval (kaijutsu extension) — baseline + challenger declared in evals.json
jutsu eval persona --evals skills/core/dream/evals/evals.json
                                                    # → 2-column report, baseline=default-claude, challenger=honest-deepseek

# 3. Per-preset eval — baseline + challenger declared in evals.json (e.g. quick vs full)
jutsu eval preset --evals skills/core/dream/evals/evals.json
                                                    # → cost+lift comparison

# 4. Per-(skill, swarm) eval
jutsu eval swarm-skill dream --preset pr-review --diff fixtures/sample.diff
                                                    # → does loading dream into a pr-review swarm catch more issues?

# 5. CI gate (strict mode) — first run seeds baseline + warns; subsequent runs hard-fail on regression
jutsu eval skill skills/core/pr-review --strict     # exits 1 only if regression vs stored baseline

# 6. agent-skills-eval compat check
jutsu eval skill third-party-skill-with-evals.json  # reads upstream-shape file unchanged

# 7. Cost guard
jutsu eval skill skills/core/pr-review --max-cost 2.00  # aborts if estimated suite cost exceeds $2
```

## Risks + Mitigations

| Risk | Mitigation |
|---|---|
| agent-skills-eval upstream changes evals.json schema | Pin compat to a tested version (`testdata/agent-skills-eval-fixtures/v1.x.y/`); bump deliberately with a compat-test diff. |
| Judge model variance produces flaky pass/fail | Document in v0.10 README; recommend `--judge claude` (lowest variance in our experience); ensemble judges as v0.10.x feature if needed. |
| Eval cost spikes on large suites (N skills × M evals × 2 sides × judge) | `--max-cost $5.00` default cost guard; hard-fail above. Mirrors v0.9 dream cost prompt. |
| Re-running evals before fixing skill regresses CI | `--strict` only fires on tag CI; manual `jutsu eval` is informational by default. |
| Swarm-shape evals produce different numbers each run (multi-agent stochasticity) | Document timing as wall-clock-influenced; pass/fail tied to assertion match, not exact output diff. |
| HTML report breaks across browsers | Minimal CSS, no JS framework, no external CSS. Render-test in chromium + safari + firefox before tagging. |
| Skill authors write trivial evals to game the gate | "Eval quality" is itself a thing eval-of-evals can measure (v0.11+). v0.10: trust the author. |

## What this spec deliberately doesn't promise

- That eval results predict real-world skill quality. They predict task-level model performance against assertions; correlation with downstream user value is empirical and multi-month to validate.
- That porting agent-skills-eval to Go preserves every CLI flag they ship. We mirror the load-bearing flags; cosmetic ones (e.g. `--log-format pretty|jsonl|silent`) ship if useful, defer if not.
- That evals.json is a stable schema. Upstream may break it; we pin compat versions.
- That single-judge grading is "objective." Judges have biases. Document; mitigate via ensemble in v0.10.x.

This is the test framework for kaijutsu's trust story. Single-skill parity proves we can run what they run; swarm-shape proves we can run what they CAN'T.
