# v0.12.0 — Tier A swarm presets (test-gap, bug-repro, code-archaeology)

**Status**: draft
**Date**: 2026-05-08
**Type**: minor (3 new swarm presets — additive surface, no behavior changes to existing presets)

---

## Why

Current swarm presets (pr-review, doc-review, brainstorm, dream, refactor-plan, security-audit, reverse) all share a "review the artifact" shape. The v0.12 additions share a different structural signature: **hypothesis generation + cross-agent ranking by evidence**. Multi-agent disagreement IS the differentiator — single-agent produces the obvious answer + misses adversarial angles.

Picks survived a `jutsu swarm dream --mode full --lenses all` adversarial pass on 7 candidates (`dep-review`, `api-review`, `test-gap`, `migrate`, `postmortem`, `code-archaeology`, `bug-repro`). Dream's swarm-value lens killed:
- `dep-review` (0.95 honest): "high-cost vibes-check on low-entropy data; AI strengths lie in subjective synthesis, not querying structured package metadata." Deterministic tools (`npm audit`, `osv-scanner`) win.
- `api-review` (0.92 time): "by 2028 native in GitHub/Copilot, kaijutsu's commodity linting redundant." Short window before subsumption.
- `migrate`: too high-stakes for a v0.12 minor. Defer.
- `postmortem`: harm-vector flagged ("authoritative blame reports enabling targeted harassment"). Needs design before shipping.

The 3 survivors all have **emergent swarm value**: imagining missing failure modes (test-gap), ranking competing hypotheses (bug-repro), generating + evidence-ranking historical theories (code-archaeology). Single-agent fails on each because each requires *generating multiple distinct candidates* and *evaluating them comparatively* — the multi-agent shape is native.

**On "swarm-value":** the bar a preset must clear is *single-agent produces a strictly worse output than multi-agent for the same task*. Worse = misses adversarial angles, narrower hypothesis space, no cross-corpus diversity check. The bar is empirical, not formal — v0.12.x will A/B test single-agent test-gap against multi-agent test-gap on benchmark fixtures to validate.

**On the apparent contradiction "shared prompts vs multi-agent disagreement":** disagreement comes from **model/corpus diversity** (claude vs gemini vs deepseek, each trained on partly-overlapping but distinct corpora), NOT from per-agent prompt specialization. The v0.5 legacy multi-agent dispatch path has shipped this way since v0.6 — same prompt, three providers, demonstrably different outputs in production swarm runs (see `~/.kaijutsu/findings.db` for evidence). Per-agent prompt specialization (à la pr-review's blunder-hunt vs paranoid-security splits) is an opt-in v0.13+ refinement when one shared prompt isn't producing enough divergence. Dream's lens-blindspot warning that "RLHF convergence may erode this premise" is real and tracked in the v0.14+ Persona SDK gate (A/B evidence required).

**Numeric scores cited above (0.95, 0.92) are confidence values from the dream session output** archived at `~/.kaijutsu/dreams/53dee208832bf970-which-of-these-7-candidate-swarm-presets-are-load-20260508-151517.md`. They reflect reviewer-assigned per-finding confidence, not external benchmarks.

Spec: this doc. Plan: `IMPLEMENTATION_PLAN.md` (3 stages, one per preset).

## Locked decisions

| # | Decision | Choice |
|---|---|---|
| 1 | Preset count | **3** (test-gap, bug-repro, code-archaeology). No padding the surface — each must clear the swarm-value bar. |
| 2 | Input kinds | `test-gap`: `InputFiles` (test file + code-under-test). `bug-repro`: `InputPrompt` (bug description) + optional file refs. `code-archaeology`: `InputFiles` (code) + git log context. |
| 3 | Per-agent prompts | **One shared prompt per preset, used by all dispatched agents.** Each preset defines its own `DefaultPrompt` (NOT the reverse-preset DefaultPrompt — each is preset-specific, sketched in the per-stage sections below). What's deferred is per-AGENT specialization (e.g., a different prompt for claude vs gemini vs deepseek), matching reverse preset's v0.9 pattern. Disagreement comes from cross-model dispatch, not dispatch-time framing. v0.13+ may add per-agent prompts if one shared prompt isn't producing enough divergence on a given preset. |
| 4 | Synthesizer shape | Each preset gets a custom synthesizer prompt that emphasizes **ranking / clustering hypotheses** rather than the standard "list findings" pattern. Output structure: top-3 ranked items + evidence + lower-confidence runners-up. |
| 5 | Confidence threshold | Default 0.30 for all 3. Justification: hypothesis-generation surfaces SPECULATIVE findings (different from pr-review's bug-hunt where high-confidence findings are the goal). Lower threshold admits speculative-but-evidence-backed candidates; the synthesizer's ranking + the user's filter via confidence column do the gatekeeping. Matches reverse preset's 0.30 (also a hypothesis-gen-style task: drift speculation requires admitting partial evidence). pr-review's 0.55 default would over-filter — many of test-gap's "what if there's a race here?" findings start under 0.55 confidence but become load-bearing once another reviewer corroborates. |
| 6 | Mode `quick` vs `full` | All 3 support both. `--full` round-robin debate uses the existing v0.8.3+ Debate primitive (`swarm.Debate(ctx, results, preset, ...)` in `cli/internal/swarm/debate.go`) — Pass-2 critique round where each agent reviews + revises Pass-1 findings, with `[new]/[disputes]/[revised]/[agreed]` tags. For these hypothesis-gen presets, Pass-2 challenges Pass-1's ranking by adding new hypotheses or contesting existing evidence. Same shape as pr-review/dream debate; no new debate mechanic. |
| 7 | Cobra surface | `jutsu swarm test-gap`, `jutsu swarm bug-repro`, `jutsu swarm code-archaeology`. Each follows the existing preset-subcommand template (`commonSwarmFlags` + preset-specific input flags). |
| 8 | Input validation + size cap | Each preset's cobra layer rejects unreadable / nonexistent file flags up front (before dispatching). Per-input size cap = 200 KB combined across all input files (matches `cli/internal/swarm/diff.go`'s diff cap). Over-cap input → cobra error with a "narrow with --files / --code or use --include filter" hint. Prevents the swarm from sending a 5 MB legacy file to remote models. |
| 9 | Error handling for git-log fetch (code-archaeology) | If `git log` fails (not a git repo, no commits touching path, gh not on PATH), preset proceeds with empty `<HISTORY>` context + a stderr warning. Theories degrade gracefully (less evidence to cite) rather than hard-failing the whole pipeline. |

## Out of scope (defer to v0.12.x or later)

- Per-agent prompt specialization (pr-review-style blunder-hunt vs paranoid-security splits). v0.13+ if user demand surfaces.
- `dep-review` / `api-review` / `migrate` / `postmortem` — explicitly deferred per Why section.
- Persona-pack or preset-pack distribution surface (v0.13 Preset SDK + v0.14+ if Persona SDK lands).
- Auto-execution of repro hypotheses (bug-repro outputs steps; doesn't run them — the "fuzzing swarm" wild-lens insight is v0.14+).
- Git-log mining for code-archaeology (we feed git log via the cobra wrapper, not via an internal git-log analyzer skill).

## Build sequence (3 stages — one preset per stage)

Each stage = preset definition + cobra subcommand + tests + skill-overrides hook + register in `defaultRegistry`. Same shape as the reverse preset's v0.9 implementation.

### Stage 1 — `test-gap` preset

**Goal**: ship `jutsu swarm test-gap` — surfaces failure scenarios MISSING from existing tests.

**Input**: code-under-test file + existing test file (or test directory). `--code <path> --tests <path>` flag pair, OR positional `<code> <tests>` args.

**Per-agent task** (single shared prompt):

> "Read the code-under-test and the existing tests. Imagine failure modes the existing tests do NOT cover. For each missing scenario, return: severity (blocker/issue/minor/info), summary (one-line scenario), reasoning (why this matters under realistic load), confidence (0.0-1.0). Skip scenarios already covered. Skip purely-theoretical scenarios that can't surface in production. Focus on: edge cases, race conditions, malformed inputs, resource exhaustion, concurrent access, integration boundaries."

**Synthesizer prompt** (custom — emphasizes ranking, not deduplication):

> "Three reviewers each proposed missing test scenarios. Cluster by failure mode (different reviewers may name the same scenario differently). For each cluster, output: cluster name, evidence (which reviewer proposed what), severity (highest across cluster), confidence (mean across cluster). Rank clusters by severity then confidence. Top output: 3-5 ranked clusters."

**Files**:
- `cli/internal/swarm/test_gap.go` — `var testGapPreset = Preset{...}` + DefaultPrompt + synthesizer prompt
- `cli/internal/swarm/registry.go::init()` — register `&testGapPreset`
- `cli/internal/cli/swarm_test_gap.go` — cobra subcommand (uses `commonSwarmFlags` + `--code` / `--tests` flags or positional)
- `cli/internal/cli/swarm.go::newSwarmCmd()` — `cmd.AddCommand(newSwarmTestGapCmd())`

**Tests**:
- `cli/internal/swarm/test_gap_test.go` — preset registers, DefaultPrompt resolves, severity vocab matches.
- `cli/internal/cli/swarm_test_gap_test.go` — cobra wiring + flag validation.

**Success criteria**:
- `jutsu swarm test-gap --help` lists the flags.
- `jutsu swarm test-gap --estimate --code <path> --tests <path>` returns a cost projection.
- All existing swarm tests stay green (no regressions to other presets).

### Stage 2 — `bug-repro` preset

**Goal**: ship `jutsu swarm bug-repro` — vague bug → ranked repro hypotheses + minimal-repro steps for top hypothesis.

**Input**: bug description (positional arg or `--bug <text>`), optional file refs (`--files <paths...>` for code context).

**Per-agent task**:

> "A user reports the following bug: <BUG>. Code context (if any): <FILES>. Generate 3-5 distinct repro hypotheses spanning different categories: state (uninitialized/stale/wrong), race condition (timing/concurrency), environment (config/version/OS/deps), input (malformed/edge/null), or version (pre-existing bug, regression, dependency change). For each hypothesis: category, summary (one-line claim), reasoning (why this could explain the bug), confidence (0.0-1.0), repro_steps (3-5 numbered steps to verify). Pick categories you think most likely; don't pad with weak guesses."

**Synthesizer prompt**:

> "Three reviewers each generated bug-repro hypotheses. Cluster by category (state, race, env, input, version). For each cluster, output: category, hypothesis text (synthesize across reviewers if they agree), evidence (which reviewers proposed it), confidence (mean), repro_steps (best version across reviewers). Rank by confidence. Output: top 3 ranked hypotheses + their repro steps; lower-confidence runners-up listed without repro steps."

**Files**:
- `cli/internal/swarm/bug_repro.go`
- `cli/internal/cli/swarm_bug_repro.go`
- Registration + tests symmetric to Stage 1.

**Success criteria**: same shape as Stage 1.

### Stage 3 — `code-archaeology` preset + housekeeping

**Goal**: ship `jutsu swarm code-archaeology` — explain WHY legacy code looks the way it does. Plus marker bump + CHANGELOG/ROADMAP/README.

**Input**: code path (positional arg or `--code <path>`) + optional `--git-log <since>` for history context (default: last 100 commits touching that path).

**Per-agent task**:

> "Read the code at <PATH>. Read the git log filtered to commits touching this path (provided in <HISTORY>). Generate 3-5 historical-context theories explaining WHY this code looks the way it does. Each theory cites evidence (commit messages, code patterns, comments, neighboring code). Categories: workaround for past bug, era-specific pattern, abandoned migration, performance optimization (now obsolete or still load-bearing), security mitigation, accidental complexity. For each: theory (one-line), category, evidence (quote/cite), confidence (0.0-1.0)."

**Synthesizer prompt**:

> "Three reviewers each generated theories about this code's history. Cluster by category. For each cluster, output: theory (synthesize), evidence (cited quotes/commits — preserve), confidence (mean across reviewers), category. Rank by confidence. Mark theories where reviewers AGREE on evidence as 'corroborated' (higher trust). Theories with conflicting evidence stay as 'contested' for the user to investigate. Output: top 3 ranked theories + evidence + provenance markers."

**Files**:
- `cli/internal/swarm/code_archaeology.go`
- `cli/internal/cli/swarm_code_archaeology.go`
- Registration + tests symmetric to Stages 1+2.

**Plus housekeeping**:
- `init_agents_fragment` marker version `0.11.0` → `0.12.0`. `init_agents_fragment_test.go` assertion updated.
- `CHANGELOG.md` `[0.12.0]` entry covering all 3 stages + dream-survival framing + deferral list (dep-review, api-review, migrate, postmortem).
- `ROADMAP.md` flips v0.12 row to [x].
- `README.md` v0.12 section: highlight new presets + when to use which.

**Success criteria**:
- `jutsu swarm --help` lists all 3 new presets.
- `jutsu init` writes AGENTS.md fragment with `version=0.12.0`.
- `go test ./... -count=1` from the `cli/` directory: every package green (currently 17 with tests + 2 no-test packages; structure may evolve).

## Risks + mitigations

| Risk | Mitigation |
|---|---|
| Per-agent task is identical → swarm dispatch is just N copies of single-agent (no diversity benefit) | Disagreement comes from cross-MODEL diversity (claude vs gemini vs deepseek trained on overlapping but distinct corpora), not dispatch-time prompt framing. v0.5 legacy multi-agent dispatch has shipped this pattern since v0.6 with demonstrably divergent outputs (see `findings.db` cross-agent disagreement counts). v0.12 ships ONE shared prompt per preset; per-AGENT specialization waits for v0.13+ if a/b shows shared prompts produce N copies of the same answer. v0.12.x will run controlled A/B (single-agent vs 3-agent shared-prompt) on benchmark fixtures to validate. |
| Stage 3 mixes preset logic + global housekeeping (breaks vertical slicing) | Defensible — same pattern as v0.10/v0.10.1/v0.11 ships. Final stage in a multi-stage release rolls in the housekeeping (CHANGELOG/README/marker) so it lands together at squash. Vertical slicing per preset is preserved within Stages 1+2; Stage 3 is the polish/ship slice. |
| Hypothesis clustering across agents is fragile (different reviewers name the same scenario differently) | Synthesizer prompt explicitly handles this ("cluster by failure mode / category"). Test fixtures pin behavior on contrived multi-agent outputs. |
| `code-archaeology` git-log fetch can be huge for old files | Default cap: last 100 commits or 50 KB of log output, whichever is smaller. `--git-log <since>` lets user override. |
| `bug-repro` repro_steps may be hallucinated and waste user time | Synthesizer marks corroborated vs single-source; user runs the corroborated steps first. Repro_steps for runners-up are NOT in v0.12 output (only the top 3 ranked hypotheses get full steps). |
| Dream's "swarm value premise unproven" warning | We accept the risk for v0.12: 3 presets is small enough surface to A/B against single-agent in v0.13.x. If single-agent test-gap matches multi-agent test-gap on benchmark, we revisit (could downgrade to skill, not preset). |
| 3 presets at once = surface bloat | v0.13 Preset SDK explicitly addresses this concern: presets become user-composable. v0.12's 3 presets become reference implementations for the SDK. |
