Schema is forward-only (consistent with v0.7).

---

## Problem

Five items share one theme: **kaijutsu's feedback loops are half-closed.** The v0.7 weighter learns from finding accept/dismiss, but only at the (preset, provider, persona) tuple — not at the lens level, so dream cells with wildly different precision profiles get smoothed together. The v0.4 PR-review posts a comment but provides no mechanism for ingesting the human's reply — the loop stops at "post". The v0.6 multi-provider work routes whole presets but not individual personas. The v0.8 dream skill ships without a Pass-2 debate, so its multi-agent value is bounded by Pass-1 quality. Spec-vs-impl drift goes undetected because no preset asks "what changed between spec and shipped code?"

Each item is small individually, but together they close the obvious gaps in the v0.7+v0.8 feedback machine. Bundling them into v0.9 (vs dribbling micro-tags) gets the schema migration done once, the routing refactor done once, the cobra-layer dream `--mode full` reject lifted once.

**Cost of doing nothing:**
- Lens-blind weighter: synthesizer can't tell that this codebase's `claude/honest` runs at 0.91 precision but `claude/gaps` at 0.42. Falls back to the tuple average. Adaptive lens-emphasis is impossible.
- No PR-comment ingest: humans accept/dismiss findings inline (the natural interaction); CLI doesn't read it; weighter starves; the v0.7 pipeline is theoretical for non-CLI-power-users.
- No reverse preset: spec-driven-development promises "the spec is the contract" but nothing checks the contract on each PR. Drift compounds silently until rediscovery.
- No per-skill routing: every multi-agent job pays for the worst-fit provider on every persona. Cost waste; quality dilution.
- Dream Pass-1-only: critique cells never get critiqued. The honest lens posts a take; nobody pushes back; sycophancy creeps back in via the synthesizer's "fold the takes" pass.

## In scope

### 1. Dream lens schema migration (`lens TEXT` column + per-lens precision)

**Status today:** v0.8.3 encodes lens as `[lens:<name>]` prefix in `summary`. `ValidDreamFinding` rejects malformed rows at recorder time. Weighter aggregates by (codebase_fp, preset, provider, persona) and is **lens-blind**.

**v0.9 changes:**

#### Migration `0002_lens.sql`

```sql
-- v0.9.0 — dream lens column + finding position. Promotes lens from
-- a [lens:<name>] prefix in summary to a first-class indexed column,
-- enabling per-lens precision tracking in the weighter. Adds
-- position for PR-comment auto-detection's stable per-finding ID.
--
-- Backfill: NULL for rows where summary doesn't carry the prefix
-- (most pre-v0.8 rows, plus non-dream presets). The recorder
-- populates lens for new dream rows; non-dream rows leave it NULL
-- forever (the column is dream-specific in spirit, but lives on the
-- shared findings table to avoid a join on every weight lookup).
--
-- position is meaningful for runs whose comments humans interact
-- with via sync-pr; old rows get NULL and sync-pr skips them with
-- a logged warning.

ALTER TABLE findings ADD COLUMN lens TEXT;
ALTER TABLE findings ADD COLUMN position INTEGER;

-- Backfill lens from [lens:<name>] summary prefix. LIKE patterns
-- side-step bracket-counting fragility; SQLite default LIKE treats
-- '[' and ']' as literals (no character-class semantics).
UPDATE findings SET lens = 'honest'     WHERE lens IS NULL AND summary LIKE '[lens:honest]%';
UPDATE findings SET lens = 'fit'        WHERE lens IS NULL AND summary LIKE '[lens:fit]%';
UPDATE findings SET lens = 'gaps'       WHERE lens IS NULL AND summary LIKE '[lens:gaps]%';
UPDATE findings SET lens = 'wild'       WHERE lens IS NULL AND summary LIKE '[lens:wild]%';
UPDATE findings SET lens = 'adversary'  WHERE lens IS NULL AND summary LIKE '[lens:adversary]%';
UPDATE findings SET lens = 'inverse'    WHERE lens IS NULL AND summary LIKE '[lens:inverse]%';
UPDATE findings SET lens = 'status-quo' WHERE lens IS NULL AND summary LIKE '[lens:status-quo]%';
UPDATE findings SET lens = 'time'       WHERE lens IS NULL AND summary LIKE '[lens:time]%';

-- The 8-lens vocabulary above MUST stay in sync with
-- swarm.DreamLensesAll() in cli/internal/swarm/preset.go. v0.9 freezes
-- the set; any future lens addition in v1.0+ requires a new migration
-- (e.g. 0003_lens_<name>.sql) that backfills new rows AND updates the
-- recorder validator's whitelist. Do NOT add lens names by editing
-- 0002 in place — migrations are forward-only.

-- Lens-aware weight lookup index. Composite layout matches the
-- weighter's lens-aware query: WHERE codebase_fp=? AND preset=?
-- AND provider=? AND persona=? AND lens=?
CREATE INDEX IF NOT EXISTS idx_findings_lens_lookup
    ON findings(codebase_fp, preset, provider, persona, lens, action_at DESC);
```

Migration is idempotent under SQLite's `IF NOT EXISTS` for the index; the two `ALTER TABLE ADD COLUMN` statements are the load-bearing steps and only run if the migration version isn't yet recorded in `schema_version`. **Both columns ship in `0002_lens.sql` as a single migration** — separate `0003_position.sql` would mean two transactions for one logical schema bump.

#### Recorder change

`RecordRun` extracts the lens from the summary prefix (re-using the existing `dreamSummaryPattern` regex) and INSERTs into the new column. **The `[lens:<name>]` prefix stays in `summary`** — it's load-bearing for the weighter's existing fallback path AND for human-readable `jutsu finding list` output that doesn't join on lens. We're widening the schema, not moving the data.

For non-dream presets: `lens = NULL` always.

#### Weighter change

`Weighter.WeightFor(meta)` gains an optional `Lens` field. Resolution:

1. If `meta.Lens != ""`: query the lens-specific tuple `(fp, preset, provider, persona, lens)`.
2. If insufficient sample (<1 actioned for cold→bootstrap; <10 for bootstrap→mature): **fall back to the tuple-without-lens average**, not to the cold default. This is the load-bearing decision: a lens with thin data inherits the persona's general precision rather than starting from scratch.
3. Cold-default applies only when both lens-specific AND tuple-aggregate are below cold threshold.

The 200-action sliding window applies independently per (tuple+lens). The query is `LIMIT 200` over the index ordered by `action_at DESC` — SQLite walks the index in reverse-time order until it has 200 actioned-non-NULL rows for the lookup tuple, then stops. Walk cost is O(window-fill): bounded by 200 returned rows but proportional to index entries traversed for tuples whose actioned rows are sparse among many pending rows. In practice, the partial pending index keeps actioned-row density high enough that the walk completes in microseconds at typical sizes (<50K rows total). At very large sizes (>1M rows with sparse actioned tuples) the walk could degrade; not a v0.9 concern, addressed by the v0.9.x prune-old-rows escape hatch. Older rows DON'T get pruned automatically — they sit in the table forever until that escape hatch ships. So 24K is the **logical working set** the weighter ever consults, not a storage cap. Physical row count grows unbounded with usage; on-disk growth is ~120 bytes/row, putting a year of heavy use (~50K rows) at ~6 MB.

#### Synthesizer change

When `preset.Name == "dream"` and weighter is non-nil, the synthesizer fetches per-lens weights and uses them to **order the synthesis output** (high-weight lenses surface higher) and to **gate the load-bearing flag** (a lens with low precision needs a stronger load_bearing signal to actually surface to the user). **When weighter is nil** (fresh install with no DB, or DB unreachable for any reason): the tier table below does NOT apply; the synthesizer falls back to its v0.8 behavior — load_bearing flag passes through, no per-lens reordering, no tier promotion or downgrade. Adaptive lens-weighting is a value-add layer; nil-weighter never breaks dream output.

Full tier rule (covers all combinations of `load_bearing` and lens weight, **weighter non-nil**):

| `load_bearing` | `lens.weight < 0.4` | `0.4 ≤ weight < 0.7` | `weight ≥ 0.7` |
|---|---|---|---|
| **true** | downgrade to "consider" tier | surface as "load-bearing" (no change) | promote to "load-bearing (high-confidence)" tier |
| **false** | surface in normal section | surface in normal section | surface in normal section |

**Surface-section semantics (resolves the "consider"-vs-load-bearing ambiguity):**
- "load-bearing (high-confidence)" tier renders in the synthesis output's **load-bearing block** with a "high-confidence" badge prefix.
- "load-bearing" tier (no modifier) renders in the load-bearing block, no badge.
- "consider" tier renders in a SEPARATE **consider** section *below* the load-bearing block — surfaced but visually de-emphasized. Findings here are still readable; the model said load_bearing=true, so we don't drop them, but the lens's poor track record means the user should evaluate before acting.
- "normal section" findings (load_bearing=false) render in the standard per-lens section as today.

So: low-weight lenses CAN'T promote a `load_bearing=false` finding into the load-bearing block (the flag is the entry point), but a low-weight lens DOES move a `load_bearing=true` finding from the load-bearing block down to the "consider" section. That demotion is intentional — it's the whole point of weight-gating.

These thresholds are starting points, not gospel; will need tuning once per-lens distributions emerge from real usage. Adding a `KAIJUTSU_LENS_WEIGHT_THRESHOLDS` env-var override is out of scope for v0.9 (premature).

### 2. PR-comment auto-detection

**Status today:** `jutsu swarm pr-review --post-comment` posts the synthesis as a single PR comment with a `<!-- kaijutsu-pr-review:run-id=… sha=… -->` marker. Humans accept/dismiss findings inline by replying. Nothing reads the replies. Loop is open.

**v0.9 change:** new subcommand `jutsu finding sync-pr <pr>` (and `--auto-sync` flag on `jutsu swarm pr-review` — fires AFTER the pr-review run completes its post-comment step, in the same invocation; non-blocking against synth) that:

1. Fetches PR conversation via TWO `gh api` calls (one PR-view doesn't return everything we need):
   - `gh api /repos/{owner}/{repo}/issues/{pr}/comments` → top-level issue/PR comments and replies (the kaijutsu marker comment + reply-keyword channel).
   - `gh api /repos/{owner}/{repo}/pulls/{pr}/comments` → line-anchored review comments (the per-finding threads from `--post-review` + their reactions sub-resource).
2. Locates the kaijutsu-pr-review comment (by marker; falls back to the most recent if marker absent).
3. Parses **two channels** of human action signal:
   - **Reply comments** containing one or more `accept: <id>` / `dismiss: <id>` lines. **Grammar (regex-formal):** each action line matches `(?im)^[\s>]*(accept|dismiss)\s*:\s*([A-Za-z0-9]+:[0-9]+)\s*$`. Notes:
     - Case-insensitive on the action verb (`Accept`, `ACCEPT`, `accept` all match).
     - Leading whitespace OR `>`-quoting tolerated (so a reply can quote the bot's marker block above an action line).
     - One id per line; **multiple action lines per reply are supported** (a reply with `accept: X:0\ndismiss: X:1` records two actions).
     - Multi-id-per-line (`accept: X:0, X:1`) is NOT supported — reduces ambiguity vs a comma in the id itself; humans wanting multiple actions write multiple lines.
     - Whitespace around the colon between verb and id is tolerated (matches dream-recorder load_bearing convention).
     - id format: `<run_id>:<position>` per the marker contract; the parser doesn't split internally — it just whole-string-matches against the marker registry.
     
     The parser scopes action keywords by THIS rule (in priority order):
     1. The comment is a threaded reply (GitHub `in_reply_to_id`) anchored at a kaijutsu-pr-review marker comment → use that comment's run-id.
     2. The comment body contains an explicit run-id reference (`run-id=<id>` text OR a quoted `<!-- kaijutsu-pr-review:run-id=<id> -->` marker line) → use the named run-id.
     3. Otherwise: the comment is IGNORED. Plain comments without scoping context don't get parsed. (Re-runs leave multiple kaijutsu-pr-review comments on a PR; without an explicit anchor, a reply could attach to any of them. Better to silently ignore than to mis-record.)
   - **GitHub reactions on per-finding review-comment threads** (NEW in v0.9 — see render change below). The default `--post-comment` mode keeps the existing single-comment renderer for backward compat, but a new `--post-review` mode posts each finding as its own line-anchored review comment via `gh api /repos/{owner}/{repo}/pulls/{pr}/comments`. Humans react with `+1` (accept) or `-1` (dismiss) on each thread; sync-pr ingests reactions via `GET .../reactions`. This sidesteps the GitHub limitation that non-author humans cannot edit the bot's comment body to add inline emoji prefixes (an attribution constraint the original spec missed).
4. For each `(run_id, finding_id, action)`: writes to the local findings DB via the existing `jutsu finding mark` codepath (so all the consistency checks fire).
5. Idempotent: prior `(run_id, finding_id)` actions are no-ops if the action matches; conflicts (e.g. user previously accepted, now dismisses) prefer the latest timestamp and emit a `[changed]` log line.

**Cross-channel timestamp resolution:** humans can act via reply-keyword AND react via `+1`/`-1` on the same finding within the same review session. Resolution rule: take the strict-latest `created_at` across both channels (GitHub's reaction timestamp is `created_at`; reply comment timestamp is also `created_at`; reply-edits update `updated_at`, but the parser only reads `created_at` for ordering — edits to a reply don't re-order an action). Tie-break: reply-keyword wins (it's the more deliberate channel). Tie within a single channel is impossible (GitHub timestamps are millisecond-resolution).

**Why two channels:**

- Reply-with-keywords is the natural "I want to leave a paragraph of reasoning AND act on findings" interaction. Works on every PR without needing the per-finding review-comment renderer.
- Per-finding reactions (via `--post-review`) is the natural "I'm reading this comment, I want a one-click accept/dismiss" interaction — and is the only inline channel that respects GitHub's edit-attribution model (non-authors cannot edit the bot's comment, but anyone can react to any comment).
- Either alone leaves a class of users out. Both fire through the same downstream codepath.

**`--post-review` (new render mode, opt-in v0.9):** posts the synthesis HEADER as the existing single-comment, then posts each finding as its own line-anchored review comment. **Each per-finding review-comment body MUST carry a `<!-- finding:<run_id>:<position> -->` marker on its first line** — same marker contract as `--post-comment`'s inline-finding markers, just split across N comment bodies instead of N marker lines in one body. sync-pr's reaction ingest path reads each review comment's body, parses the marker, then fetches that comment's reactions via `GET /repos/{owner}/{repo}/pulls/comments/{id}/reactions`. The marker is the load-bearing link; reaction → comment-id → marker → `(run_id, position)`.

**Line-anchor source for `--post-review`:** the existing `swarm.Finding` schema already carries `file string` and `line_range string` (e.g. `"42-58"`). The renderer maps these to GitHub's review-comment fields:
- `path` ← `finding.file`
- `line` ← lower bound of `line_range` (the parser splits on `-`)
- `side` ← `RIGHT` (commenting on the new state of the file)
- `commit_id` ← head SHA of the PR

**Fallback when a finding lacks a file anchor** (synthesis-level findings, multi-file findings, or the rare schema-violating Pass-1 result with empty file): the renderer falls back to posting that specific finding as an INLINE marker line inside the header single-comment, NOT as a per-finding review thread. So `--post-review` always succeeds; per-finding review comments are best-effort, and findings without a clean line-anchor degrade gracefully into the same render path as `--post-comment` for those entries only.

Trade-offs vs the single-comment mode: more PR noise, but enables the cleanest per-finding interaction; revertible via `--post-comment` (default).

**Permission model:** by default `sync-pr` runs read-only — fetches state, prints a diff of "would mark these findings as X". `--apply` actually writes. `--auto-sync` on `pr-review` implies `--apply`. Mirrors `jutsu finding clear`'s dry-run-default discipline.

**The `<!-- finding:<id> -->` marker:** new contract. The pr-review synthesizer renderer must emit a stable per-finding marker. ID format: `<run_id>:<finding_position>` (e.g. `20260507T164647Z:3`). The colon delimiter avoids hyphen collisions with future UUID-style run IDs. Position is 0-indexed within the run. NOT the DB autoincrement — those don't exist yet at render time. The recorder stores position via the `position INTEGER` column added in migration `0002_lens.sql` (above), populated at INSERT time by the recorder's loop counter.

**Scope: pr-review only in v0.9.** The `<!-- finding:<id> -->` marker convention applies only to the pr-review preset's renderer. `jutsu finding sync-pr` filters comments by proximity to a `<!-- kaijutsu-pr-review:run-id=… -->` block, so reverse-preset comments (which carry their own `<!-- kaijutsu-reverse:… -->` marker) are ignored. Cross-preset action ingest is a v1.0 candidate. Concurrent presets posting on the same PR (pr-review + reverse via `--reverse-spec`) get DISTINCT marker prefixes so per-finding IDs cannot collide across presets.

### 3. Reverse swarm preset (`jutsu swarm reverse`)

**Status today:** swarm presets reason **forward**: spec → review of impl-against-spec, code → review of code-against-itself, idea → exploration. Nothing reasons **reverse**: take an impl (PR diff) and a spec, ask "what does the impl do that the spec didn't authorize, and what does the spec require that the impl ignores?"

**v0.9 change:** new preset `reverse` registered alongside `pr-review` / `doc-review` / etc. Consumes:

- **Spec input** (path arg or `--spec <file>`): markdown file, typically the spec doc that authorized the work.
- **Diff input** (path arg or `--diff <range>`, defaults to `origin/main...HEAD`): the implementation under review.

Per-agent prompt skeleton:

```
You are auditing for spec-vs-impl drift. The spec authorized a set of
changes; the diff is what was actually shipped. Your job is to find
the gap.

Categorize every drift finding into ONE of:

- ADDED: in the diff, NOT mentioned in the spec
- OMITTED: in the spec, NOT in the diff
- CHANGED: spec said one thing, diff did a different thing
- AMBIGUOUS: spec was vague, diff made a choice — flag the choice

For each finding emit:
  severity: blocker | issue | minor | info
  category: ADDED | OMITTED | CHANGED | AMBIGUOUS
  spec_quote: the specific line/section from the spec (or "n/a" for ADDED)
  diff_evidence: the file:lines from the diff (or "n/a" for OMITTED)
  reasoning: why this is drift, not legitimate scope adjustment

DO NOT flag:
- Code-quality issues (other presets cover that)
- Style nits
- Drift that the spec EXPLICITLY blesses ("see also: X" / "out of scope")

DO flag:
- Out-of-scope items shipped silently
- Non-goals violated
- Acceptance criteria not met
- Risk-mitigations promised but not implemented
```

**Synthesizer:** reuses pr-review's cluster-then-table renderer. The drift table has columns: `severity`, `category`, `spec_quote`, `diff_evidence`, `reasoning`. Output goes to stdout (TTY) or markdown comment (`--post-comment` writes a kaijutsu-reverse comment with its own marker prefix).

**When it runs:** designed for two triggers:

1. **Manual**: `jutsu swarm reverse --spec docs/specs/foo.md --diff origin/main...HEAD` before merging a feature PR.
2. **Implicit on pr-review**: `jutsu swarm pr-review --reverse-spec docs/specs/foo.md` runs both presets back-to-back. Reverse output is a separate section in the PR comment.

**Boundary against pr-review's domain:** pr-review reasons about code-quality (bugs, security, style, scope-creep within the diff). Reverse reasons about spec-vs-impl drift (what the diff did or didn't do *relative to the spec*). The boundary is fuzzy — "scope creep" findings can land in either preset. v0.9 tolerates the overlap: under the `--reverse-spec` combined trigger, both presets run and post DISTINCT comment blocks (different marker prefixes), so the human sees both sections and can read each on its own terms. Cross-preset finding de-dup is a v1.0 candidate (likely needing a shared finding fingerprint that survives across preset renderers). Until then: prefer pr-review for code-quality framing, prefer reverse for spec-anchored framing, expect occasional doubles.

**Confidence bias:** drift detection is harder than code review (requires reasoning across two artifacts). The preset ships with a **confidence threshold of 0.30** (vs the default 0.55 used by pr-review's synthesizer) — admits roughly 2× more findings, biased toward false-positives over false-negatives. Tunable via `--confidence-threshold <float>` if 0.30 turns out wrong. The **lie-to-them filter** (the v0.7 sycophancy-suppressor that drops findings whose phrasing matches a "validate-the-user" pattern) is OFF by default for reverse — false-positive "drift" findings are easier to dismiss than false-negative misses. Override via `--lie-to-them=on` if the user finds reverse output too soft.

**Reuse:** the existing `synth.go` clustering + table render pipeline is preset-agnostic; reverse plugs in via the standard `Preset` struct. No new infra.

### 4. Per-skill provider routing

**Status today:** `cli/internal/swarm/skill_prompts.go` resolves prompts per-(preset, agent). The agent name (`claude` / `codex` / `gemini`) is the routing key. Persona mode (v0.6) overlays personas on top, but routing is uniform: every persona dispatches to the underlying provider declared at persona-registry time.

**Reality:** different skills+personas have different ideal providers. Empirically:
- **honest lens**: tends to perform best on whichever model has the strongest "skip pleasantries" instruction-following. Claude > Codex > Gemini in our limited testing.
- **adversary lens**: benefits from divergent thinking; rotating providers across runs surfaces different attack surfaces.
- **brainstorm**: same — diversity > raw-quality.
- **security-audit**: prefers models with code-execution comprehension — Claude or Codex; Gemini's results often surface UI-level concerns missing the actual exploit.

This is anecdotal. The right answer is to **let skill authors declare preferences** and let users override.

**v0.9 change:** new optional `routing:` block in `skill.yaml`:

```yaml
routing:
  # Preferred provider list per persona, ordered. Swarm picks the first
  # available one when assembling the persona's job. Falls back to
  # whatever the persona registry says if all preferred are unavailable.
  per-persona:
    honest:    [claude, codex]
    adversary: [claude, codex, gemini]   # diverse > best
    gaps:      [claude]
    wild:      []                         # no preference; use registry default
  # Global fallback when persona isn't named above.
  default: [claude, codex, gemini]
```

JSON schema for `routing` (added to `schemas/skill.schema.json`):

```json
"routing": {
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "per-persona": {
      "type": "object",
      "additionalProperties": {
        "type": "array",
        "items": {"enum": ["claude", "codex", "gemini"]}
      }
    },
    "default": {
      "type": "array",
      "items": {"enum": ["claude", "codex", "gemini"]}
    }
  }
}
```

**Resolution algorithm in swarm dispatch — two distinct phases:**

```
PHASE A — Resolve a preferred-provider list for each persona
(does NOT consult availability):

    1. If skill.yaml routing.per-persona has the persona name:
       use that list (in declaration order).
    2. Else if skill.yaml routing.default is non-empty:
       use that list.
    3. Else: use the persona registry's default mapping
       (existing v0.6 behavior; one entry — the registry default).

  Phase A always produces a non-empty preferred-provider list.

PHASE B — Pick a runnable provider from the preferred list,
consulting available_providers (the agents detected at runtime):

    4. Walk the preferred list in order; take the first provider
       that's in available_providers.
    5. If none of the preferred providers are available:
       - With --strict-routing: hard-fail listing the missing
         providers and the persona affected.
       - Without --strict-routing: drop the persona from this run
         with a stderr warning ("persona X skipped: preferred
         providers <list> all unavailable; pass --strict-routing
         to fail hard, or fix routing to include an available
         provider").

PHASE C — Minimum-dispatch invariant (only meaningful with
                                       --strict-routing OFF):

    6. (--strict-routing ON: Phase B already hard-failed on the
       first persona drop, so Phase C is unreachable. Skip.)
    7. (--strict-routing OFF) After Phase B completes, count the
       personas that survived (got a runnable provider).
    8. If zero: hard-fail with error: "no personas dispatchable for
       preset X — all preferred providers unavailable; check
       --personas, agent registry, and skill.yaml routing". This
       invariant exists so --strict-routing OFF doesn't silently
       turn into "run nothing and pretend you did".
```

`--strict-routing` fires in Phase B on the first per-persona unavailability. Phase A is purely declarative and always succeeds. Phase C is the catch-all for the `--strict-routing OFF` path — it converts the corner case "Phase B silently dropped EVERY persona" into a hard fail, since silent zero-dispatch would produce empty output indistinguishable from "no findings". With `--strict-routing ON`, the same scenario hard-fails earlier in Phase B; Phase C is a no-op.

**Override:** users can set `routing.disabled: true` in `~/.kaijutsu/agents.yaml` to ignore skill-declared routing entirely (use registry defaults). This is the escape hatch when a skill's preferences are wrong for the user's setup.

**No backwards-compat shim needed:** existing skills without `routing:` get nil block → step 4 fallback → identical behavior to today.

### 5. Dream-flavored Pass-2 debate template

**Status today:** `cli/internal/swarm/preset.go` declares `dreamPreset.Debate = dreamDebatePlaceholder`, which instructs agents to return `[]`. The cobra layer rejects `--mode full` for dream upfront. Pass-2 is dead-letter for dream.

**v0.9 change:** real Pass-2 debate template + cobra reject lifted.

#### Debate template (per-agent prompt for Pass-2)

```
You are critiquing a peer's dream-lens output. You ALREADY emitted
your own thoughts on this topic (shown below as YOUR ORIGINAL).
You now have your peers' thoughts (shown below as PEERS).

For each PEER thought, decide ONE of:

- agree: peer's thought is load-bearing AND your original missed it
  → emit a [new] entry adopting the peer's framing, attributed
- disagree: peer's thought is wrong / soft / sycophantic / misframed
  → emit a [disputes] entry stating WHY (specific, no hedging)
- redundant: peer's thought is essentially what you already said,
  perhaps differently worded
  → omit; do NOT emit anything for this thought

For each of YOUR ORIGINAL thoughts:

- if peers' inputs revealed a load-bearing flaw, emit a [revised]
  entry with the corrected version
- if peers' inputs reinforced your original (independent agreement
  on the same thought across agents), emit a [agreed] entry
  marking it as cross-agent corroborated. NOTE: [agreed] is only
  meaningful with peer count >= 2. With a single peer (e.g. when
  per-skill routing collapses a lens to one provider), [agreed] is
  unreachable; emit [revised] / [new] / nothing instead.

Output is a JSON array. Each element MUST start the summary field
with one of:
- [lens:<name>] [new] <thought>
- [lens:<name>] [disputes] <peer's claim> — <your counter>
- [lens:<name>] [revised] <updated thought>
- [lens:<name>] [agreed] <thought>

(The [lens:<name>] prefix carries forward from Pass-1 — you must
preserve which lens this thought lives in. The square-bracket
revision tag goes AFTER the lens prefix.)

Do NOT:
- Pile on with "great point" / "I agree" without a [agreed] tag
  pointing to a specific cross-agent match.
- Emit empty arrays just to be polite. Empty IS a valid output if
  peers added nothing load-bearing AND your originals stand
  unchanged.

YOUR ORIGINAL OPTIONS:
%s

PEERS' OPTIONS:
%s
```

The format mirrors pr-review's debate template (`[new]` / `[disputes]` / `[revised]` / `[agreed]` revision tags) but adds the `[lens:<name>]` prefix preservation rule. The synthesizer's existing dream renderer already handles these revision tags via `MergePasses` — no synthesizer change needed.

#### Cobra reject lift

`cli/internal/cli/swarm.go` currently has a check rejecting `--mode full` when `preset.Name == "dream"`. v0.9 removes that check. `--mode full` runs Pass-1 → Debate (with the new template) → Synthesize via `MergePasses`-aware path. The graveyard auto-write stores the merged result.

#### Cost guard

Pass-2 doubles agent cost. Dream's matrix (lenses × personas) is already wider than other presets. v0.9 adds a soft warning:

```
$ jutsu swarm dream --mode full ...
This will dispatch <n> Pass-1 cells × <m> agents + Pass-2 critique.
Estimated cost: $X.YZ. Continue? [y/N]
```

Bypass with `--yes` (matches existing flag). Estimate uses the existing `cost.go` helpers; no new pricing data needed.

**Non-TTY / CI behavior:** if stdin isn't a TTY (typical for CI runners or piped invocations), the cost prompt does NOT block waiting for input. Instead it prints the estimate to stderr and HARD-FAILS unless `--yes` was passed, with error: `dream --mode full requires interactive confirmation or --yes; refusing to dispatch a non-trivial cost run silently`. This mirrors the v0.7 destructive-default-off discipline: the safe default in non-interactive contexts is "don't spend money", not "spend it without asking".

**Pricing data freshness:** `cost.go` ships hardcoded per-model rates that are accurate as-of release. If providers change pricing between releases, estimates drift — surfaces in the prompt header as `(prices as of <build-date>)`. Doesn't break workflow; user sees a sanity-check estimate, not a billing line item. Auto-refresh from a remote pricing source is out of scope for v0.9 (network round-trip on every cost prompt is worse than mild drift).

#### Lens-rotation rule (the half-shipped v0.8.3 piece)

This v0.8.3 deferral lands in v0.9 alongside Pass-2: when `--mode full` AND `FindRecentDreamForTopic(topic, fp, 7d)` returns a hit, the LEAD lens rotates to the next one in `DreamLensesAll()` canonical order. **Canonical order is fixed: `honest → fit → gaps → wild → adversary → inverse → status-quo → time → honest` (cycle).** Previous run led with `honest` → next leads with `fit`; previous led with `time` → next leads with `honest`. Rotation surfaces a different framing on repeat-dreams without forcing the user to remember `--lenses=...`. Standalone `/dream` (single-Claude) inherits the same rule via the skill-level prompt instruction (already in place since v0.8.0).

## Out of scope

- **Cross-codebase weighter aggregation** — per-codebase precision stays per-codebase. Lens schema makes this *possible* later but not now.
- **GitHub Pull Request *Reviews* API** (the formal "approve / request changes / comment" review-submission endpoint, distinct from individual review comments) for accept/dismiss as a structured review verdict. v0.9 uses the pull-request-comments endpoint (`/pulls/{pr}/comments`) for `--post-review` thread creation and reads reactions on those comments — that's a different surface than submitting a top-level Review with `event=APPROVE`. Submitting actual Reviews is a v1.0 candidate.
- **Reverse preset across multiple specs** (multi-spec drift detection). v0.9 takes one spec at a time.
- **Auto-route based on observed precision** — routing is author-declared in v0.9; auto-routing from the weighter's per-(provider, persona, lens) precision is v1.0+.
- **Streaming Pass-2** — same blocking matrix model as Pass-1, run sequentially after Pass-1 completes.
- **Auto-rotate lens on repeat dreams beyond LEAD** — only the LEAD rotates in v0.9; full-list rotation is overkill (each lens appears anyway).
- **Reverse preset auto-discovery of the spec** — user passes `--spec` explicitly. Auto-finding `docs/specs/<branch-name>.md` is convenient but brittle; defer to v1.0.

## Migration strategy

1. **Schema migration `0002_lens.sql`** runs automatically on first `jutsu swarm dream` / `jutsu finding *` invocation under v0.9. Idempotent. Adds `lens` and `position` columns; backfills `lens` from summary prefix; creates the lens-aware lookup index.
2. **Existing v0.7/v0.8 findings DBs** get backfilled lens values for rows whose summary starts with `[lens:<known>]`. Other rows: `lens=NULL`, `position=NULL`.
3. **Old CLI versions** running against a v0.9-migrated DB: the schema is forward-compatible (extra columns are ignored by older code that doesn't `SELECT lens`). No old-CLI breakage.
4. **`skill.yaml` `routing:` field** is OPTIONAL; existing skills work unchanged.
5. **Reverse preset** is purely additive — no existing preset behavior changes.
6. **PR-comment marker `<!-- finding:<id> -->`** is purely additive in pr-review's renderer. Old comments without it are still parsable by humans; the sync-pr parser warns on findings missing markers.

No down-migration. No flag-day cutover. No deprecation cycle needed.

## Open questions (for doc-review to chew on)

1. **Lens-weight thresholds (0.4 / 0.7)** are guessed, not measured. Acceptable for ship; will need tuning once we have a few weeks of per-lens action data. (Killswitch decided in spec body: `KAIJUTSU_DREAM_ADAPTIVE_LENS=off` ships in v0.9 — see Risks table. Open question is purely about the threshold values, not the killswitch existence.)

2. **`<!-- finding:<id> -->` marker stability under comment edits.** If a human deletes the marker by mistake (manual edit), sync-pr loses the link. Mitigation: parser also accepts `accept:<id>` / `dismiss:<id>` keywords as a fallback channel, and warns if marker count drops between runs of the same run_id. Strong-enough? Or do we need a "marker integrity check" subcommand?

3. **Reverse preset's spec parsing.** Today's spec docs are markdown with H2 sections like `## In scope` / `## Out of scope` — natural anchor points. Should the reverse prompt teach agents about kaijutsu's spec-doc convention (`## In scope`, `## Out of scope`, `## Open questions`)? **Tentative: yes, but as a soft hint, not a hard requirement** — many teams won't follow this exact convention.

4. **Pass-2 debate cost guard threshold.** Currently always prompts when `--mode full` for dream. Should there be a `--budget <dollars>` flag that auto-rejects above a ceiling without prompt? **Tentative: defer to v0.9.x** — first ship the bare prompt, observe how often it fires.

5. **Reverse preset on a draft PR with unfinished impl** — drift findings will be massive (most of the spec is "OMITTED"). Should the preset auto-detect "PR is marked draft" via `gh pr view` and emit a softer header? **Tentative: yes, low cost, high signal.**

## Build sequence (5 stages)

### Stage 1 — Schema migration + recorder lens column

**Goal:** `0002_lens.sql` ships, recorder writes `lens` + `position`, weighter optionally consumes `lens` (no-op when not provided). Existing DB rows get backfilled on migration.

**Success criteria:**
- `jutsu finding list` works against pre-v0.9 and post-v0.9 DBs identically.
- Manually inspecting a freshly-recorded dream run shows `lens` populated and `position` 0..N-1.
- Weighter test passes both with and without `meta.Lens` set.

**Tests:**
- `TestMigration0002_BackfillsExistingDreamRows`
- `TestMigration0002_HandlesEmptyDB` (idempotent on first-install)
- `TestRecorder_WritesLensAndPosition`
- `TestWeighter_LensFallsBackToTuple`
- `TestFindingSeed_DevOnlyFlagGated` (the dev-mode seed subcommand used by the verification recipe is gated behind `--dev` / `KAIJUTSU_FINDING_SEED=1`; production CLI rejects with "unknown command")
- `TestFindingSeed_InsertsActionedRows` (verifies the seed correctly populates user_action + action_at so the weighter sees mature-tier samples)

### Stage 2 — Synthesizer adaptive lens-weighting + lens-rotation rule

**Goal:** dream synthesizer reads per-lens weights, reorders output, gates load_bearing tier. LEAD lens rotates on repeat-within-7d.

**Success criteria:**
- Two synthesis runs against same dream output but different weighter state produce different lens ordering.
- Repeat dream within 7d shows different LEAD lens (verified via written graveyard headers).

**Tests:**
- `TestSynthesizeDream_ReordersByLensWeight`
- `TestSynthesizeDream_LoadBearingTierGating`
- `TestRotateLeadLens_OnRepeatWithin7d`

### Stage 3 — Dream Pass-2 debate template + cobra reject lift

**Goal:** `--mode full` runs end-to-end for dream; merged output writes to graveyard; cost-prompt fires before dispatch.

**Success criteria:**
- `jutsu swarm dream --mode full --topic "X" --yes` completes; output contains AT LEAST ONE revision tag from `{[new], [disputes], [revised], [agreed]}`. (`[agreed]` requires ≥2 peers per lens; with single-peer fixtures or persona-collapsed routing, only the other three are reachable. Test fixtures pin ≥2 peers per lens to keep `[agreed]` reachable for the integration test.)
- Cost-prompt fires without `--yes` and waits for stdin.

**Tests:**
- `TestDreamDebateTemplate_PreservesLensPrefix`
- `TestSwarmDream_ModeFullEndToEnd` (integration; uses fake-providers)
- `TestDreamModeFullCostPrompt`

### Stage 4 — Reverse swarm preset

**Goal:** `jutsu swarm reverse --spec X --diff Y` runs end-to-end; produces drift table; `--post-comment` posts under the kaijutsu-reverse marker.

**Success criteria:**
- Run against a spec/diff pair where 1 thing was added off-spec, 1 thing was omitted, 1 thing was changed → all 3 surface in the right category.
- Posted comment body fits under GitHub's 65,536-byte limit for a single PR comment; tables encode multi-line cell content with `<br>` (no raw newlines inside `|`-delimited cells); fenced code blocks nest at most one level deep (no quadruple-backtick edge cases).
- **Oversize-output handling:** if the rendered drift report exceeds 60,000 bytes (4KB safety margin under GitHub's 65,536-byte limit), the renderer truncates: posts the top-N findings ranked by `(severity, file_path, line_range_start)` — severity primary (blocker > issue > minor > info), file_path lexicographic for ties, line_range_start numeric for further ties — until under cap, with a footer line `… <K> more findings truncated. Run \`jutsu swarm reverse\` locally for the full report.` and dumps the full report to stderr in the same invocation. The deterministic tie-break ordering means the same input always produces the same truncation point. No gist auto-creation (would scatter output across services).

**Tests:**
- `TestReversePreset_DispatchesPerAgent`
- `TestReverseSynth_ClusterByCategory`
- `TestReverse_DraftPRSofterHeader`

### Stage 5 — Per-skill routing + PR-comment auto-detection

**Goal:** `routing:` field parsed from skill.yaml; swarm dispatch respects it; `<!-- finding:<id> -->` marker emitted; `jutsu finding sync-pr <pr>` parses the comment + replies; weighter receives accept/dismiss writes.

**Success criteria:**
- Skill with `routing.per-persona.honest: [claude]` against an environment with claude+codex+gemini → only claude dispatches for honest persona.
- `--post-review` mode posts per-finding line-anchored review comments; a `+1` reaction on one thread → `jutsu finding sync-pr <pr> --apply` records the accept; a `-1` reaction → records the dismiss; `jutsu finding list` reflects both.
- Reply comment with `accept: <run-id>:0\ndismiss: <run-id>:1` does the same via the reply channel (works against the default `--post-comment` single-comment renderer too).

**Tests (Stage 5):**
- `TestSkillRouting_PerPersonaPreference`
- `TestSkillRouting_FallbackChain`
- `TestSkillRouting_PhaseCMinDispatchInvariant`
- `TestSyncPR_ParsesReactionMarkers` (uses recorded `gh api` JSON fixtures stored under `cli/internal/swarm/testdata/sync-pr/` — captured once via `gh api ... --jq` against a real PR, then committed; tests stub `gh` execution via `os/exec` indirection)

## Verification (end-to-end)

```bash
# 1. Migrate
jutsu finding list                       # triggers 0002_lens migration; warns 0 rows had lens
sqlite3 ~/.kaijutsu/findings.db ".schema findings"   # has lens, position columns

# 2. Adaptive lens-weighting
# Pre-seed weighter state so the (provider, persona, lens) tuple is
# in MATURE mode (>= 10 actioned findings); 2-3 cold-mode runs would
# stay below the bootstrap threshold and produce no observable
# ordering shift, falsely failing this verification.
jutsu finding seed --provider claude --persona honest \
  --lens honest --accepts 9 --dismisses 1   # mature, ~0.9 precision
jutsu finding seed --provider claude --persona gaps \
  --lens gaps   --accepts 4 --dismisses 6   # mature, ~0.4 precision
jutsu swarm dream --topic "Should we add Y?"
# Synthesis output orders 'honest' lens cells higher than 'gaps' cells
# AND surfaces honest-lens load_bearing findings at promoted tier
# while down-weighting gaps-lens load_bearing findings to "consider".

# Note: `jutsu finding seed` is a v0.9 dev/test affordance only,
# behind the --dev flag (or KAIJUTSU_FINDING_SEED=1). Production CLIs
# don't expose it. Implementation detail: programmatic INSERT into
# the findings table with synthetic run_ids prefixed `seed-`.

# 3. Pass-2 dream
jutsu swarm dream --topic "X" --mode full --yes
# Synthesis output contains [new] / [agreed] / [disputes] tags
ls ~/.kaijutsu/dreams/                   # latest header has mode: full

# 4. Lens rotation
jutsu swarm dream --topic "X"            # LEAD: honest
jutsu swarm dream --topic "X"            # within 7d → LEAD: fit (rotation)
jutsu dream list                         # both runs visible

# 5. Reverse preset
jutsu swarm reverse --spec docs/specs/foo.md --diff origin/main...HEAD
# Drift table with ADDED / OMITTED / CHANGED / AMBIGUOUS columns

# 6. Per-skill routing
jutsu swarm pr-review                    # observe in stderr: dispatch chose claude for honest persona

# 7. PR-comment auto-detection — reaction channel (--post-review mode)
jutsu swarm pr-review --post-review      # posts per-finding line-anchored review comments
gh pr view 42 --json comments,reviewThreads   # observe per-finding threads
# (human reacts +1 on one thread, -1 on another, via the GitHub UI or:
#  gh api /repos/<o>/<r>/pulls/comments/<id>/reactions -f content=+1 )
jutsu finding sync-pr 42                 # dry-run: shows "would mark abc-0:0 accepted, abc-0:1 dismissed"
jutsu finding sync-pr 42 --apply         # writes
jutsu finding list                       # the actions landed

# 7b. PR-comment auto-detection — reply channel (works with default --post-comment)
jutsu swarm pr-review --post-comment     # single-comment renderer (existing default)
# (human posts a reply: "accept: 20260507T164647Z:0\ndismiss: 20260507T164647Z:1")
jutsu finding sync-pr 42 --apply         # parses reply, records both actions

# 8. Strict routing — sanity-check
# Setup: configure pr-review skill.yaml routing to require gemini for
# at least one persona, then make gemini unavailable. v0.9 adds a new
# env-var KAIJUTSU_DISABLE_AGENTS=<comma-list> (added in this release
# alongside Phase B/C dispatch) for testing — drops the named drivers
# from agent detection without uninstalling them. Listed in Touches.
KAIJUTSU_DISABLE_AGENTS=gemini jutsu swarm pr-review --strict-routing
# Expected stderr: "routing: persona <name> requires preferred provider
#                   gemini which is unavailable; --strict-routing is
#                   set, hard-failing"
# Exit code: non-zero (1)
```

## Risks + Mitigations

| Risk | Mitigation |
|---|---|
| Migration runs against a corrupted v0.7/v0.8 DB and partially backfills | Migration is wrapped in a single transaction; failure rolls back; user keeps existing data unchanged. |
| Migration transaction stalls on very large DBs (>1M rows) due to 8 sequential UPDATE statements | At expected v0.9 scales (≤50K rows), the 8 backfill UPDATEs complete in well under a second on SQLite. Beyond ~1M rows, the single-tx approach holds a write-lock for seconds — ship a chunked-backfill escape hatch (`--migrate-chunked`) in v0.9.x if any user reports lock contention. v0.9 does not pre-build it (premature). |
| Per-lens windows fragment the precision data (each window thinner) | Fallback to tuple-without-lens precision when lens-specific window is below cold threshold. Net effect: lens data REFINES when available, doesn't STARVE when absent. |
| Reverse preset surfaces too many false-positive "drift" findings against a spec the team has informally diverged from | Lower confidence threshold + lie-to-them OFF balanced by clear `AMBIGUOUS` category — let the human triage. |
| `<!-- finding:<id> -->` marker scheme breaks if humans edit the comment in surprising ways | Reply-keyword channel is a fallback; sync-pr emits warnings on marker drift; `--apply` is opt-in. |
| Pass-2 dream cost spike for matrix-heavy users (8 lenses × 5 personas) | Cost prompt before dispatch; default OFF; behind explicit `--mode full`. |
| Per-skill routing locks users into the skill author's biases | `routing.disabled: true` user override; per-skill preferences are the FALLBACK after persona registry, not above. |
| Lens-weight thresholds (0.4 / 0.7) wrong for some codebases | Killswitch env-var (`KAIJUTSU_DREAM_ADAPTIVE_LENS=off`); thresholds easy to tune in v0.9.x patch without breaking schema. |

## Decisions deferred to implementation

These are non-load-bearing choices likely to surface during implementation but not worth resolving at spec time:

- Position counter scope: per-run, per-(run, persona), or per-(run, persona, lens)? **Working assumption:** per-run, monotonic across all findings in the run. Simplest; matches the comment-render order; collisions impossible.
- Reverse preset's marker prefix: `<!-- kaijutsu-reverse:run-id=… sha=… -->`, by analogy with pr-review.
- Routing fallback to registry default: should it require `routing.default: []` to be present, or implicit-empty? **Working assumption:** omitting `routing.default` AND explicitly setting `routing.default: []` are EQUIVALENT — both fall through Phase A step 2 to step 3 (registry default). Authors who want zero preferences expressed can omit; authors who want to document "deliberately no preference" can write `[]`.
- Whether `jutsu finding sync-pr` should also create new findings for human-authored "missed bug" comments. **Working assumption: NO** — keep sync-pr scoped to ingesting actions on bot-emitted findings. Net-new human findings is a separate feature.

## What this spec deliberately doesn't promise

- That adaptive lens-weighting is the *right* algorithm. It's *a* starting algorithm; the real work is observing the per-lens distribution and tuning. v0.9 ships the machinery, not the wisdom.
- That reverse preset catches all spec drift. It catches what models can read in the spec and the diff. Implicit drift (what the team intended but didn't write down) is invisible to it. Use as one signal, not the signal.
- That per-skill routing is more than a heuristic. The real win is the *infrastructure*; the per-skill lists in skill.yaml are guesses that real usage will overwrite.
- That the Pass-2 debate template is the final form. It's the v1; observation will surface revisions.

This is plumbing. The wisdom comes after the data does.
